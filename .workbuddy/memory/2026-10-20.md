## 顺手抓到的真问题：覆盖率扫描器静默错读（100% → 14%）

做 STATS 第一次实跑 `_c2s_coverage.py`，输出 **19/134 = 14%**，不是报告里的 134/134。
根因：当天早前未记档的并发重构把 `_dispatch` 拆成「包装方法 + `_dispatch_locked`」
（RLock 临界区），分支体整体搬走；扫描器只扫 `def _dispatch(` 到下一个方法，
**110+ 条分支全部漏掉**。而这个脚本**没挂回归**——33/33 全绿没人发现，报告数字早已过期。

三件事堵洞（都在 `协议资料/报告/_c2s_coverage.py`）：
1. 扫描段延伸到 `_dispatch_locked` 末尾（存在时）；
2. **分支数下限守卫** `MIN_BRANCHES = 40`：扫到的 if/elif 不够就 `RuntimeError` →
   main  catch 后 rc=2（实测全量 110 条，余量充足；突变验证：下限改 1000 精确判红）；
3. 抽出 `compute()`（不打印、返回事实 dict）供 STATS 复用，打印输出逐字不变。
修复后 134/134 恢复。**已挂进回归 ① 层**（静态，约 1.3s）。

发帧时打不了标：`m4_server` 不认识 `tap`（FakeConn 测试要能不挂 tap 裸跑）。
改为**事后按 seq 区间回填**：

```python
lo = tap.last_seq(); r = srv.gm_war_start(); hi = tap.last_seq()
tap.mark_range(lo + 1, hi, 'GM 开战', kind='war_start')
```

成立的前提是 `gm_war_*` 全程持 `_lock` 同步跑完，期间无别的线程插帧——锁的这条保证
正好是 `_test_gm_lock` 早就守着的。所以这里没有新增任何锁，只是利用了已有的临界区性质。

## 踩到并修掉的三个边界 bug（都是测试逼出来的）

1. **`tap.frames(since=N)` 是开区间**（`seq > N`）。直接拿 `since=lo` 取链路会**静默**
   丢掉首帧——首帧恰好是 `WarStart(112)`，最该看见的那一帧。改用 `since=lo-1` 取。
2. **两段链路共用 `last_seq()` 当边界**：开战段 `hi` 与胜利段 `lo` 同值，区间是闭的，
   那一帧同时属于两段（两段都标红）。下界改 `last_seq() + 1`。
3. **被拒的命令记下空段落**：不在战斗中时点「一键胜利」，一帧不发，但仍记了
   `{lo:86, hi:86, frames:0}`，`mark_kinds.war_win` 还 +1。界面显示「GM 胜利 #86-86（0 帧）」，
   看的人会以为点漏了或链路没发帧，实际是**命令被拒**。改成 `hi > lo` 才记段落。
   （`/api/action` 与 `/api/gm/cmd` 两处都修——漏一个入口等于一半链路没标，而界面不报错。）

## 顺带修掉的进程退出崩溃

测试全绿但退出码 `0xC0000409`（`Fatal Python error: _enter_buffered_busy`）。
根因不是本次改动：内核 `handle` 线程是 daemon，`srv.stop()` 不打断阻塞在内存管道
`recv` 里的它；解释器关闭时它若正卡在 `print()` 上就与 stdout 缓冲锁相争。
修法：teardown 里 `srv._stop = True` → `client_end.close()`（投递哨兵让 recv 返回 b''）
→ `srv.stop()` → **`kernel_th.join(5.0)`**。`subprocess` 的 `capture_output` 同样会留
一条读管道的守护线程，一并改成重定向到文件。改完连跑两次 `EXIT=0`。

> 通用教训：daemon 线程只是「不阻止退出」，不等于「退出时是安全的」。
> 只要它会 `print`，就必须显式 join。

## 先说查到的真相：表有、接口有、**面板一行都没渲染**

`FEATURE_STATUS`（12 条）→ `feature_status()` / `op_feature_map()` → `GET /api/features`
整条数据链是通的。但 `gm_dashboard.html` 里**完全没引用** `features`——

「GM 面板 /api/state 会带出来」，实际 `gm_state_dict()` 里没有它。
**注释与实现不一致，比没写注释更坏**：后来人照着注释去找，找不到会怀疑是自己看错。

顺带发现 `feature_note()` 被注释提到两次，但**函数根本不存在**（grep = 0）。
一并修掉注释，不补空函数（没人调用，补了就是死代码）。

## 实现

1. **`FEATURE_STATUS_LEGEND`**（模块级）：状态 → 人话，6 档。
   原先图例写死在 `_GMHandler.do_GET` 的 dict 里、文档里又一份——改档位要改两处。
2. **`FEATURE_TITLE`**（模块级）：键 → 中文名。面板不该显示 `craft_levelup` 这种裸键名。
   与状态**分开存**：状态是代码事实（会变），标题是固定名称（不该随进度变）。
   混在一起的话，改状态时很容易顺手把标题也改坏。
3. **`feature_rows()`**：拼好 `key/title/status/desc/rank` 并按严重度排序。
   前端不排序、不映射文案——插一句就是第二份规则，迟早漂移。
4. **`/api/features` 增加 `rows`**，`legend` 改用 `feature_legend()`（单一来源）。
5. **`gm_dashboard.html`**：新增通栏「特性状态」卡片。缺口排最前，
   缺口红 / preview_only 深红 / simulated 蓝 / ignored 灰 / implemented 绿。
   刷新策略：开机拉一次 + 60s 兜底，**内容签名没变就不重绘**——
   这是代码事实，一个会话里不变；每 1.2s 重绘会把用户正在读的地方刷没。

## 踩到的一个自造坑：两套序号

加一档要改两处，漏一处就**排错且不报错**。改成同一个数（`_FEATURE_SEVERITY`），
并且**测试直接引 `m._FEATURE_SEVERITY`**——测试里再抄一份就守不住了。
