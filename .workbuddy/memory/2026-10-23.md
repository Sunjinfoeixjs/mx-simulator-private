### 关键教训
- **必然事件不抽随机数**。`chance(p)` 在 `p<=0/p>=1` 直接返回、`choice()` 单候选同理。
  否则「把某概率从 0 调成 1」会连带改变后续所有流的取值，排查时无法解释。
  副作用：测试里用 `chance=1.0` 验「是否会抽」永远得 0 —— 这**不是**链路没走，
  是没必要掷。测试必须用 `0<p<1` 才能验抽取计数。
- **`_mix32` 不能用内置 `hash()`**：Python 3 字符串 hash 带进程级随机化，
  同一流名跨进程会派生不同种子，"跨进程可复现"直接没。
- **拆决策函数要防重复抽取**。初版 `_enemy_attack` 调了两次 `decide()`（一次选目标、
  一次决定动作），随机消耗翻倍、同种子复现失效。根因：「查保护」需要先知道打谁，
  而「放不放招」又依赖有没有保护 → 顺序天然是三步，硬塞一个函数只能回调或重复抽。
  改成 `pick_target()` + `decide_action()` 两步式。
- **变异打不红 = 覆盖漏洞，不是变异构造错**。M2（taken_mul 覆盖 vs 相乘）没红，
  因为只挂了一个 `taken_mul` 状态；M5（去掉进度上限）没红，因为 `0+3` 恰好等于
  `NEED=3`，`min()` 有没有都一样。补的断言本身是该守的行为，不是硬凑。
- **改随机源会连带打红三个既有测试**：`_test_pet_skill` / `_test_common_ops` /
  `_test_state_consistency` 都在 `mock.patch.object(m.random, ...)` 或
  `random.seed()`。改打桩对象、**断言一条不动**——打桩的是实现细节，不是行为。
- **5 个测试文件硬编码了不存在的路径** `服务端源码\sim`（正确是 `tests/sim`）：
  `_test_war2` / `_test_drop` / `_test_enemy_skills` / `_test_battle_speed` /
  `_test_singleplayer`。能跑只因 runner 注入了 PYTHONPATH；单跑必 ModuleNotFoundError。
