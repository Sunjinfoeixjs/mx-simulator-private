## 1. 传输帧格式（★S2C 与 C2S **不对称**，不能互推）

| 方向 | 布局 | 长度字段 N |
|---|---|---|
| S2C（服务器→客户端） | `[N 1B][payload N]`，`payload[0] = opcode` | **含** opcode |
| C2S（客户端→服务器） | `[opcode 1B][N 1B][body N]` | **不含** opcode |
| 两向共同 | `N == 0xFF` 时长度扩展为 `0xFF + 2B u16 LE` | — |

### 1.1 S2C〔A：原生层反汇编〕

`mxmain.dll FUN_00430fe0`（收包主循环）逐字节逻辑：

```
[1B 长度前缀 N][payload N 字节]
  N == 0xFF 时：扩展为 [0xFF][2B u16 长度 LE][payload]
  payload[0] = opcode（1 字节）        ← FUN_00430fe0 取 payload[0] 放入对象 +4
  payload[1:] = 数据体（脚本层 UnpackInt/UnpackString 读取）
```

- 长度 N **含 opcode**（对象 +5 处记录 `N-1` 为数据体长度）〔A〕
- 加密开关：对象 +0x72 字节 != 0 时收发经 `0x43cc50` 流密码；== 0 明文〔A〕
  （补丁 DLL `mxmain_nocrypto.dll` 已将 +0x72 置零 → 全链路明文**可跑通**〔C〕）
- 注：`0x430fe0` 只是**收包**循环，它管不到发送方向——旧版据此推断 C2S 同格式，见 §1.3。

### 1.2 C2S〔C：真机运行观测〕

```
[opcode 1B][长度 N 1B][body N 字节]
  N == 0xFF 时：扩展为 [opcode][0xFF][2B u16 长度 LE][body]
  N 不含 opcode（N 就是 body 的字节数）
```

三条互相独立的运行证据：

1. **内核日志**（`服务端源码/logs/m4_srv_*.log`，解析器即 `m4_server.recv_c2s`）：
   帧头首个字节总是客户端 `net.py` 里的 `C2S_*` 常量，第二个字节恰为 body 长度——
   例 `③ C2S opcode=54 body=5B: 2d 00 28 00 00`（x=45, y=40, trace 空），
   `opcode=2 body=5B: 01 00 00 00 00`（进世界 id=1）。
   若按「长度在前」解析，首个字节会被当成 N、连接立刻失步，而本仓 m2/m4 内核自
   2026-10-15 起一直用这套解析跑完**全部真机会话**。
2. **独立分帧器**（`tools/sim/tap.py:_parse_one`，只按字节流分帧、不经过内核解析）：
   2026-10-19 真机会话 1033 帧、32 种 C2S opcode，`desync=0 / dropped=0`
   （`报告/真机实验记录_op100_op101.md` §1）。长度口径哪怕差 1 字节，帧会立即错位。
3. **字段三角一致**：tap 解出的字段与服务端 `build_*` 发射值、与玩家真实操作逐条对得上
   （如 `op=101 pos=5` → `op=99 index=4 amount=1` 对应实买「变身宝珠」），
   说明 body 起点没偏。

旁证（二手）：`报告/客户端网络层解析_20261018.md` §2.1 给出同一张表，并记「与
`make_s2c`/`make_c2s` 逐字节一致」。

### 1.3 勘误：旧版「双向同格式（对称协议）」是模拟器的自证

旧版此处写「客户端 / 服务器**双向同格式**（对称协议）」。该结论**没有任何 C2S 观测支撑**，
来源已追溯到三处，全部是同一假设的自我闭环：

| 环节 | 问题 |
|---|---|
| `tools/sim/entry_protocol_sim.py:PacketSend()` | 自行按 `[1B 长度][opcode][body]` 包装上行帧，注释写「按 0x430fe0 确认」——而 0x430fe0 是**收包**函数 |
| `tools/sim/mock_server_min.py:parse_login_frame()` | 沿用同一假设解析登录流，于是 M1 阶段那声「解析成功」只是假设内部自洽 |
| `logs/mock_srv_*_after_handshake.bin`（113B） | **不是真客户端字节**，而是 `entry_protocol_sim.build_c2s_login_in()` 同族输出：填充值逐字节一致（`adsid=0x1234567890ABCDEF` → `78 56 34 12`、`driveid=0xDEADBEEF` → `ef be ad de`、假 MAC `"00:1A:2B:3C:4D:5E"`），首字节 `70` 是模拟器自己写的长度前缀；比当前生成器多 1 字节（opcode 后多一个 `00`，早期版本）。<br>复现：`python -c "import entry_protocol_sim as e; print(e.build_c2s_login_in('100860001','abcdef').PacketSend().hex(' '))"` → `6f 01 00 0a 2b 00 … 00:1A:2B:3C:4D:5E`。 |

→ 结论：**该 bin 不能当「实测抓包」引用**；真客户端在同一位置发的是 `[op][N][body]`。
（M4 规格 §0 自 2026-10-15 起写的就是正确的不对称格式，本次是 M1 向 M4 对齐。）

## 2. 握手序列（非代理连接）

客户端 `selectserver.Connect()` → `net.CNet.Connect(ip, port)`（脚本层不发任何数据）〔B〕：

```
① 客户端 TCP 连接 3134                    （NakedSend 8B 仅在代理模式发送！）〔B〕
② 服务器下发 S2CHello 帧：               opcode=1                     〔A 字段序 / C 实发〕
     [N=7][01][seed 4B LE][servernum 2B LE]
     → 帧字节: 07 01 XX XX XX XX SS SS
③ 客户端 SetSeed(seed)、m_Hello=True，回 25B NakedSend（明文，不加密）：〔B 构造 / C 实发〕
     前 3B = 混淆后 seed 小端，后 22B = 0x00
④ 客户端显示登录界面（loginin.ShowLogin()）                            〔C：截图 + 真机〕
⑤ 用户输入账号密码 → 发 C2SLoginIn 帧  （opcode=1，见 §4）              〔C：真机日志〕
```

真机实证：`logs/mock_srv_*.log` 的 `② Hello PASS ✓（16 ed 4b）` —— 25B 回应的前 3 字节
与 §3 公式算出的一致〔C〕。

## 3. Hello 种子混淆公式（客户端 netlogin.S2CHello）

```
seed = UnpackInt(4)                # 服务器 Hello 帧的 4B seed
SetSeed(seed)
seed = (0x100000000 + seed) % 3227993 + 2562088 ^ 6636321
NakedSend(chr(seed%256) + chr((seed//256)%256) + chr((seed//65536)%256)
          + '\x00' + '\x00'*21)    # 共 25 字节
```

**★C0 常量：已定论 = `0x100000000`（4294967296 = 2^32）**〔A〕，非旧会话标注的 `0x400000000`。

定论证据（2026-10-15，来自原始 marshal 字节，非反编译二次产物）：
- `S2CHello` consts[4] 原始字节 `6c 03 00 00 00 00 00 00 00 04 00`，按标准 CPython 2.6 marshal 的 **15-bit digit** 语义 = 2^32〔A〕；
- 同文件锚点：`adsid & 4294967295L` 掩码原始字节 `6c 03 00 00 00 ff 7f ff 7f 03 00` → 15-bit 语义 = 0xFFFFFFFF（恰为 32 位掩码，语义自洽）〔A〕；
- 旁证 `src/prop.py` 的 `return i + j * 4294967296L`（高/低 32 位拼 64 位）同样印证 2^32 语义〔B〕。

运行校验：真机 25B 回应可被本仓 `hello_response()` 逐字节重现〔C〕。

根因：`tools/pymarshal26.py` 的 `TYPE_LONG` 曾用 **16-bit 拼接**读 long，导致 >2^30 的 long 常量被放大 4 倍
（0x100000000 → 0x400000000），进而污染 protocol_crypto.py / entry_protocol_sim.py 的 `HELLO_C0`。已一并修正。

## 4. C2S 登录包（C2SLoginIn，opcode=1）

`netlogin.C2SLoginIn(name, pwd)` 字段顺序〔B〕（帧内 payload[1:] 依次）：

| 字段 | 宽度 | 说明 | 等级 |
|---|---|---|---|
| CLIENT_SCRIPT_VERSION[0] | 1B | 脚本版本 (0) | 〔B〕〔C 观测：`00 0a 2b 00`〕 |
| CLIENT_SCRIPT_VERSION[1] | 1B | (10) | 〔B〕〔C〕 |
| CLIENT_SCRIPT_VERSION[2] | 2B | (43) | 〔B〕〔C〕 |
| name | 32B | 账号，GBK，`\x00` 补齐 | 〔B〕〔C：日志能解出账号〕 |
| pwd | 20B | 密码，明文 | 〔B〕（真机日志只校验账号，密码未单独验过） |
| C_sys.GetVersion()[0..2] | 1B/1B/2B | 客户端版本 | 〔B〕 |
| update.ini Version[0..2] | 1B/1B/2B | 1.x.y → (x, y) | 〔B〕 |
| localip[0..3] | 4×1B | 本机 IP（g_OverdoVersion 时伪造 192.168.x.x） | 〔B〕声明 /〔D〕宽度 |
| adsid>>32 | 4B | 广告 ID 高 32 | 〔B〕/〔D〕 |
| adsid & 0xFFFFFFFF | 4B | 低 32 | 〔B〕/〔D〕 |
| len(tgId) | 1B | 推广 ID 长度（通常 0） | 〔B〕/〔D〕 |
| tgId | len | 推广 ID | 〔B〕/〔D〕 |
| driveid | 4B | 硬盘序列号 | 〔B〕/〔D〕 |
| mac | len | MAC 字符串 | 〔B〕/〔D〕 |

**★ 尾部宽度未坐实（2026-10-22 观测；〔C〕与〔B〕冲突，按〔D〕记）**：按上表累加，
mac 为 17 字符时应为 99B；真机日志实测到 **60B 与 94B 两种** body 长度
（`m4_srv_*.log`：`C2S opcode=1 body=60B` / `body=94B`，同为 `00 0a 2b 00` + name32 + pwd20 开头）。
说明尾部字段在此构建里存在可变/缺省形态，**不要把 §4 的累加宽度当契约**。
对模拟服无影响：登录判定只读 `body[4:36]`（账号），要求 `len(body) >= 56`。

## 5. S2C 登录响应帧（服务器→客户端）〔B：netlogin/net.py 读序；C：真机可见效果〕

| opcode | 处理函数 | 字段布局（payload[1:]） |
|---|---|---|
| 1 | S2CHello | seed(4B) + servernum(2B) |
| 2 | S2CLoginAccountInfo | Count(1B) + CurrentTime(4B) + vid(1B)；Count==0 → EnterSelectRole（选角界面）；Count>0 → 随后 N 个 S2CLoginRoleInfo |
| 3 | S2CLoginRoleInfo | ID(4B)+time(4B)+Icon(1B)+Shape(2B)+Desc(2B)+Level(1B)+School(1B)+Race(1B)+Point(4B signed)+Name(16B) |
| 5 | S2CLoginQueue | queue_pos(2B)（排队） |
| 8 | S2CLoginError | err_id(1B)（登录错误） |
| 30 | S2CLoginMessage | isub(1B) + 变长（多益通升级等提示） |

**模拟服最小推进方案**：收 C2SLoginIn 后回 opcode=2 帧 `[N=7][02][Count=0][time 4B][vid=1]`
→ 客户端进入**选角界面**（M1 达成〔C：真机截图〕）。如需角色列表，则 Count=N 后依次发 N 个 opcode=3 帧。

## 7. 加密层现状

- 补丁 DLL（+0x72=0）→ 全链路明文，M1 可跑通〔C〕
- 未补丁时收发经 `0x43cc50` 流密码，算法位于 VMProtect 区段
  （5006i44r / 6gu4zq7g / c7ktdw0v，VA 0x598000），静态不可读〔E〕
- 还原路径：动态抓 (seed, 明文, 密文) 三元组 + 脱壳静态分析（见 protocol_crypto.py recovery_plan）〔E 未完成〕
