## 二、资源引用链（已实证）

客户端脚本里，战斗单位（怪物 / 宠物 / 玩家）统一走 `CWalkerBase`：

```
core/walker.py:575   LoadSpr(state)
    filename = path + '/%s.spr' % state        # path = GetResPath(charidx,...)
    data = C_sys.LoadFile(filename, 'char')    # 资源组固定为 'char'
    回退链：char/<shape>/<state>.spr
            → char/hero/0111/<NN>/<state>.spr   （仅 attackN）
            → char/2010/<state>.spr 或 char/0000/<state>.spr
```

- 造型 id = `m_CharIdx`（服务端下发的 `shape`）。怪物从 **2130** 起（玩家 < 1000）。
- `<state>`：`stand` / `walk` / `attack1` / `hurt` / `die` 等，见 `walker._state`。
- 战斗特效与飘字另走 `war` 组：`war/shit/eff.spr`（会心红字，`core/warrior.py:127`）、`war/hit/`、`war/lineup/%.2d.igs`。
- 图标资源：宠物技能图标 = `skill` 组 `'%.3d.igs' % petskill.GetShape(skid)`；道具在 `item` 组。

**推论**：新增一只怪 = 新增 `<shape>/{stand,walk,attack1,hurt,die}.spr` + 它们引用的帧图 `.igs`，全部在 `char` 组（`char.fls`，705 MB / 9,338 条目）。

## 三、图像格式（反编译实证）

`mxmain.dll` 反编译（`客户端源码/dll_export/decompiled_all.c`）：

- `FUN_004586e0`：`Read(file, hdr, 0xe)` —— **固定 14 字节头**
- 头布局（实测 `war/00000_00A01E99.res`）：`magic(2) version(2) bpp(2) width(2) height(2) anchorX(2) anchorY(2)`
  - 该样本：`I0 / 1 / 16 / 68 / 80 / (31,43)`
- 6 种 magic → 4 个解码器（`FUN_00458660` 分派）：

| magic | 解码器 | 样本量（war 93 个） |
|---|---|---|
| `I0` `I2` | `FUN_00458050` | I0 = 73 |
| `I1` `I3` | `FUN_004581b0` | I1 = 20 |
| `I4` `I6` | `FUN_00458310` | 0 |
| `I5` `I7` | `FUN_00458470` | 0 |

- `I0` 读法（`FUN_00458050`）：读 4 字节 count → 分配 `count*3` 调色板 + `count` 字节 run 表 →
  逐行按 run 长度铺色。即**调色板 + 按行 RLE**，不是裸位图；`bpp=16` 走 0x200 字节的宽色分支。
- `char` 组 4,588 个 `.res`，magic 分布 `I0` 387 / `I1` 13（抽样 400）。

> 待验：帧数如何表达（同一 `.res` 是否含多帧，还是每帧一个条目）。头部 14 字节里没有帧数字段，
> 目前更可能是「一帧一条目」，帧序由 `.spr` 文本描述 —— 需要用 `.spr` 实物确认。

## 四、注入缺口

| 缺口 | 现状 | 解法 | 成本 |
|---|---|---|---|
| `.fls` 写回 | ✅ **已完成**（`tools/fls_pack.py`：preserve 字节一致 / compact 变长） | — | 0 |
| `I0` 容器级编解码 | ✅ **已完成**（`tools/i0.py`：解析→重编码字节一致，war 93/93） | — | 0 |
| 条目名 → f0 | 资源归档 33,534 条**全部匿名**（只有 346 条脚本名已对） | 移植 `StringID` + `CCache::CalID` 规范化，用 346 条 ground truth 验证 | 中 |
| `.res` → PNG | 无 | 移植 `FUN_00458050`/`FUN_004581b0`；**先定宽高来源**（见下） | 中偏高 |
| PNG → `.res` | ❌ 阻塞：`.res` 头的 `w*h` 与 `FUN_00457bf0` 收到的宽高不是同一组数（war#0 头 68×80 但按 `w*h*8` 要 43,520B > payload 32,353B） | 读 `FUN_004587b0`（完整加载 + `CGetInfo`）定宽高，再对齐 `.spr` 帧描述 | 高 |
| `.spr` 文本 | 部分 `.bin` 仍是加密态（`char` 4,396 条） | 已有 4 字节 XOR 密钥链（`fls格式规范.md`） | 低 |

**关键利好**：`StringID`（`0x443ef0`）、`CCache::CalID`（`0x440ce0`）、四个图像解码器**全在反编译 C 里**，
不需要再动 Ghidra，纯移植即可。

### 哈希细节（已读通，未移植）

```
CCache::CalID(name, group):
    id = StringID(normalize(name))
    if group: id ^= StringID(normalize(group))
normalize: ASCII 小写→大写；'\\' → '/'；遇到 >=0x80 的 DBCS 双字节则跳过第二个字节
StringID: 自定义 32-bit 哈希，初值 0xf4fa8928 / 0x37a8470e / 0x7758b42b，
          常量 0x9be74448 / 0x66f42c48 / 0x267b0b11，掩码 0xbfef7fdf / 0x7dfefbff / 0x2040801 / 0x804021
```

## 五、三条路线

| 路线 | 做法 | 代价 | 适用 |
|---|---|---|---|
| **A. 替换现有条目** | 不动名字，只把某个已有 `.res` payload 换掉（长度可变，重写索引） | **已打通**（`fls_pack.py` + `i0.py`；14 项断言见 `报告/fls写回与资源替换_20261022.md` §六） | 换现有资源的内容（换 body / 改头） |
| **B. 新增完整资源** | packer + hasher 全上，新增 `<shape>/*.spr` 与新帧图 | 高（缺 hasher + `.spr` 文本格式 + 像素编码） | 真正的「新怪物」mod |
| **C. 散文件** | 归档未命中时原生会回退读 `<group>\<name>`（相对客户端工作目录，异步） | 低（**但只对新增资源有效**，不能覆盖已有条目） | 试造型/试贴图，前提是能起新名字 |

**路线 C 的静态结论（2026-10-22）**：回退分支在 `FUN_00403b50`（图像/精灵加载器），
`CFile::Open(name,group,"rb")` 失败且 `group != NULL` 时拼 `group + "\\" + name`，
经 `FUN_00440440` 建任务、`FUN_00410d90` 入队（异步）。`FUN_00421eb0`（`.igs`/`.occ`）没有回退。
→ **归档优先**，散文件只在 miss 时兜底；要用它必须“起一个新名字”（新造型 id）。
待验：`FUN_00448af0` 对 `.SPR/.TXT/.MGC/.PFM/.INI/.DLG` 的特殊分支是否意味着这些扩展名总是读磁盘（未坐实）。
实验步骤见 `报告/fls写回与资源替换_20261022.md` §五。

## 六、fal 出图规格（管线打通后填实）

已知硬约束（来自真实资源）：

- 透明底、单体、居中，锚点在脚底偏上（样本 `anchor=(31,43)`，尺寸 68×80，约为脚底中心）
- 同一造型 5 个状态、每个状态若干帧 → **一致性靠「一张基准图 + 编辑派生」**，不要一次画整张表
- 交付格式：PNG（RGBA）→ 转 `I0`/`I1` `.res`

待定项（须等 packer 打通后从 `.spr` 与真实帧反推）：帧数、单帧画布尺寸、朝向左/右、每帧时长。
