# 客户端网络层解析（2026-10-18）

> 对象：`客户端源码/src/net.py`（594 行）+ 42 个 `net*.py` 处理器（合计 21,713 行）+ `mxmain.dll` 原生编解码。
> 目的：把「客户端怎么收发、怎么分派、哪些上行还没实现」讲清楚，并顺手核掉三处会影响真值判断的东西。

## 一、这一层是三层，不是一层

| 层 | 位置 | 职责 | 规模 |
|---|---|---|---|
| 原生编解码 | `mxmain.dll`（`CNetClient`） | 帧收发、`UnpackInt/UnpackBit/UnpackString`、`PacketPrepare/Add/Send`、录像写入 | 反编译 7,416 函数 / 292,560 行 C |
| 分派 | `src/net.py` | opcode → 处理函数、四种执行策略（立即 / 战斗队列 / 延迟队列 / 特殊） | 594 行 |
| 处理 | `src/net*.py` 42 个模块 | 解字段、写全局对象、驱动 UI | 21,713 行 |

关键结构判断：**客户端没有「会话」概念，全局单例**（`net.g_Net`、`hero.g_Prop`、`war.g_War`）。
和模拟服那边一样，这也是「单连接」成为正确性前提的根因，而不是设计选择。

## 二、编解码：帧格式好抄，位序不好猜

### 2.1 帧格式

| 方向 | 布局 | 长度字段含义 |
|---|---|---|
| S2C | `[1B N][op][body]`，N ≥ 0xFF 时 `[0xFF][u16 N][op][body]` | N **含** opcode |
| C2S | `[op][1B N][body]`，同理 `[op][0xFF][u16 N][body]` | N **不含** opcode |

与模拟服 `make_s2c` / `make_c2s` 逐字节一致，此前已由端到端测试对拍（`tests/_test_tap.py` 用真实客户端 socket 收帧比对）。

### 2.2 `UnpackBit` 的位序 —— 反汇编实证

这条被写错过至少两次（`tap.py`、`_mwr_export.py` 都写过 LSB 版），所以这次落到指令级。

`UnpackBit` 在方法表里有两个条目（两个类各一份），都只是薄包装：

```
0x41A910 / 0x41AA40   →  调 PyArg_ParseTuple(args, "ii", &off, &n)
                      →  取 netobj 缓冲指针
                      →  call 0x41A4D0 (buf, off, n, &out)
```

核心在 `0x41A4D0`，还原出来是：

```c
if (off > 7 || n < 1 || off + n > 8) return 0;      // 位域不许跨字节
byte = peek_byte();
mask = 0;
for (i = 0; i < n; i++) mask |= 0x80 >> (off + i);  // ★ off=0 → 0x80 → 最高位
v = (byte & mask) >> (8 - n - off);
```

`0x80 >> off` 这一句就是全部答案：**`off` 从最高位数，MSB-first**。

推论（与 `src/netwar.py` 一一对应）：

| 编码 | 客户端读法 | 线上字节 |
|---|---|---|
| `WarWState(123)` | `hurt=UnpackBit(0,4)` `life=UnpackBit(4,2)` `ward=UnpackBit(6,2)` | `(hurt<<4)\|(life<<2)\|ward` |
| `WarAdd(115)` | `allied=UnpackBit(0,1)` | `allied` 在 `0x80` |

另外两个约束值得记住：位域**不能跨字节**（`off+n<=8`），且 `n=0` 直接失败——所以任何「跨字节位域」的协议猜测都是错的。

### 2.3 `UnpackSigned` 的边界

`net.py:463` 是纯 Python 实现：

```python
if size < 4 and n & (128 << (size-1)*8):  return n - (1 << size*8)
```

`size < 4` 意味着 **4 字节有符号数不在这里翻转**，靠原生 `UnpackInt(4)` 直接返回 int32。
所以「4B 有符号」和「1/2B 有符号」走的是两条路，读代码时容易误判成 bug。

### 2.4 长文本分片

`C2S_TEXT(86)` 是唯一一个多帧拼装的协议（`net.py:471`）：

```
[86][1B sub=1]                 开始
[86][1B sub=2][1B len][len B]  数据，每片 ≤240B，重复
[86][1B sub=3]                 结束
```

## 三、分派：168 条路由 + 一个没人写下来的 flag 位域

### 3.1 路由表是三元组

```python
NET_FUNCTION_NAME = {123: ('netwar', 'S2CWarWState', 18), ...}
```

第三个元素**不是**「帧类型」或「优先级」注解，而是一个 **flag 位域**，在 `GetFunc` 里被塞进 `m_WarCmd[opcode]`：

```python
if len(m) > 2 and type(m[2]) == int:
    self.m_WarCmd[icmd] = m[2]
```

`OnServerCmd` 再用它决定这一帧怎么执行：

| bit | 值 | 语义 | 命中数 |
|---|---|---|---|
| 1 | `0x01` | **包成 `war.CCmd` 战斗命令对象**，进演出队列；不是立刻执行 | 11 |
| 2 | `0x02` | 触发 `WriteRecordFile()`（`.mwr` 录像检查点） | — |
| 16 | `0x10` | 若 `g_CmdDelay` 生效（对话/过场），帧进 `g_DelayQueue` 延后重放 | 6 |

实际出现过的组合：`0`（168-52=116 条，立即执行）、`1`、`3`、`16`、`18`（19 条，战斗帧主力）、`19`。

**这就是「帧序即因果」在客户端侧的机制**：带 bit1 的帧不进主循环，而是排队给战斗演出逐条消费；`WarStart` 带 bit16，所以在对话流程里会先压住、等 `ClearCmdDelay` 再放。模拟服那边把「AddNpc 必须在 SceneM 之后」当经验规则，其实客户端这边有明确的开关。

### 3.2 `SPECIAL_SERVER_CMD`：三条绕过一切的 opcode

```python
SPECIAL_SERVER_CMD = {166: True, 167: True, 170: True}
```

这三个在 `OnSpecialServerCmd` 里**不管是否在战斗中、是否在延迟队列里**，直接执行。
`167`（`S2CPlayerChat`）还多一层特判：先读 1B 频道号，`ch in (7,8,13)` 才入延迟队列，其余立即处理——即「战斗频道的喊话要跟着演出走，世界频道立刻显示」。

### 3.3 `g_CmdDelay`：一个会把帧「存起来晚点执行」的全局开关

`CreateCmdDelay(t)` 起一个 `t*30` 帧的定时器；期间所有带 bit16 的帧被塞进 `g_DelayQueue`，定时器到期由 `ClearCmdDelay` 逐条重放——**重放时仍按原顺序，且重新走「战斗中→战斗队列」的判断**。

这条路径解释了模拟服调试时的一个现象：对话中点开战，帧不会丢，而是在对话关闭后一次性涌出来。所以调试台看到的「帧序」与玩家看到的「演出顺序」不是一回事，中间隔着一个队列。

## 五、三个发现（都会影响「真值」的可信度）

### 5.1 位序已在二进制层实证，模拟服是对的

见 §2.2。这条结论现在是**指令级**证据，不再是「注释里这么说」。

### 5.2 137 份 `.mwr` 全是自录，不能当官方真值

`_mwr_export.py` 原注释写「2013 年真机对战录像，服务端真实下发帧」——**不成立**：

```
0137.mwr  2026-10-18 10:58
0124.mwr  2026-10-18 10:5x
0001.mwr  2026-10-15 14:03
```

游戏早已停服，`D:\mxsj2013\client\record` 里 138 个文件全部落在 **2026-10-15 ~ 10-18**，都是本项目自己连模拟服时录的。
录制逻辑是 `net.py:OnServerCmd` 里 `if f & 2: WriteRecordFile()` —— **录的就是刚收到的字节**，客户端并不校验位域是否合法。

所以这类语料只能回答「客户端收到了什么」，**不能**用来证伪模拟服的编码选择；一旦模拟服发错，录像会忠实地把错误存下来，再被当成真值回读。这是一个闭环自证陷阱。

### 5.3 语料里其实有两套编码，混在一起了

按 WState 的位域字节分组，23 个文件干净地分成两族：

| 族 | 文件 | 字节 | 按正确位序解 | 按 LSB 位序解 |
|---|---|---|---|---|
| 旧（≤0118，8 个文件） | 92 帧 | 只有 `0x40` / `0x60` | `hurt=4/6` ← **非法值** | `hurt=0, life=0/2, ward=1` ← 合理 |
| 新（0119+，15 个文件） | 47 帧 | `0x01` / `0x09` / `0x11` | `hurt=0, life=0/2, ward=1` ← 合理 | `0x11 → hurt=1 life=1 ward=0` ← 错位 |

旧族那 92 帧只能是「当时模拟服按 LSB 打包」的产物——`tap.py` 里那个错位拆法不是凭空来的，它当年和内核是配套的，后来内核改成 MSB 而解码层没跟。

**这也意味着：旧族 8 个文件（约 46% 的 WState 样本）在任何统计里都不该再计入。**

**已隔离（2026-10-18）**：`_mwr_export.py` 现在逐份判定代际，默认跳过旧族。

判据刻意**不用文件序号**（序号会随新录像失效，且看不出「哪一份坏了」），而是用协议事实：
客户端 `UnpackBit(0,4)` 取 hurt，只有 0（普通）/1（会心）两个值，所以
**`(bits>>4)&0xF > 1` 在正确编码下不可能出现**。旧族的 `0x40/0x60` 正好落在这一侧。

```
录像 137 个；帧 1999（采用 1534 / 压缩 0）
  位域代际：current 15 / legacy 8 / unknown 114
  ⚠ 已跳过 8 个旧族录像（LSB 打包期…）：0021 0035 0037 0106 0112 0113 0114 0118
  采用 129 个录像 / 1534 帧
```

- 只在**出现过 WState**的录像上判定；整份没有 WState 的记为 `unknown` 并保留——
  它污染不了位域统计，没必要连地形/NPC 帧一起丢。
- 要强行纳入加 `--include-legacy`，输出里会一直提示口径不同。
- `录像真值_战斗帧_20261018.csv` 已按新口径重导（1999 → 1534 行）。
- 回归：`tests/_test_mwr_family.py`（判据 + 整份判定 + 真实文件抽查 0021/0124）。

### 5.4 「会心率随造型」的结论是错位序 + 混族造成的假象

`数值与协议真值审计_20261018.md §8.2` 给出：企鹅 0/63 不会心、野狼 11/11 全红，据此落地 `ENEMY_HURT_BS_BY_SHAPE = {1: 0.0, 2130: 1.0}`。

用**正确位序 + 只取新族**、并按 `WarAdd` 的 uid→shape 与 `AttackNormal` 的攻守配对重算：

| 施法者造型 | 命中 | hurt=0 | hurt=1 |
|---|---:|---:|---:|
| 1（梦想企鹅） | 12 | 12 | 0 |
| 2130（野狼） | 2 | 1 | 1 |
| 4005 | 13 | 13 | 0 |

原统计之所以得出「野狼 11/11 全红」，是因为野狼只出现在**新族**文件里，而新族字节以 `0x01` 为主，被 LSB 拆法读成 `hurt=1`；企鹅样本主要来自**旧族**，`0x40` 被读成 `hurt=0`。**族别与造型完全重合，于是「编码差异」被误读成「怪物差异」。**

正确口径下的结论：企鹅 0/12、4005 0/13 与「不会心」一致；野狼只有 2 个有效样本（1 红 1 橙），**不足以支持「必红」**。`{1: 0.0, 2130: 1.0}` 应视为未验证——在此之前它等于把假象写进了玩法。

**已处理（2026-10-18 13:45）**：`ENEMY_HURT_BS_BY_SHAPE` 清空为 `{}`，所有造型统一走 `ENEMY_HURT_BS_CHANCE = 0.35`；机制（按造型登记）保留，注释写明「什么条件下才该填：同一造型 ≥30 次有效命中，且样本必须来自新族录像」。

顺带修掉一个被这张表掩盖的注入缺陷：`_start_war` 原来直接覆写 `self.enemy_hurt_bs_chance`，而 `__init__` 的注释又说「实例属性便于测试注入」——两者冲突，`_e2e_m7` 注入的 `1.0` 一直是**靠表里恰好也是 1.0** 才生效。表清空后注入会被改成 0.35、断言随机失败。现拆成两个字段：`enemy_hurt_bs_chance` 为显式覆盖（`None` = 自动），`_hurt_bs_chance` 是开战时解析出的本场实际值，掷骰只用后者。

### 5.5 不只是 WState：WarAdd 也有两代编码

做录像导出时才发现的——同一批语料里 `WarAdd(115)` 的位域**位置**不同：

| 代 | 文件数 | `allied` 位 | 证据 |
|---|---:|---|---|
| new | 19 | bit7 (`0x80`) | `0124.mwr`：主角 `…00 80 00 00 01…` |
| old | 118 | bit0 (`0x01`) | `0001.mwr`：主角 `…00 01 00 00 01…` |

这正是 `m4_server.build_war_add` 注释里记的那条历史 bug（「历史上按 LSB 发送导致全单位
allied=0，玩家出现在对面」）。**它的影响范围比位域本身大**：任何按 allied 分组的统计
（我方承伤 / 敌方承伤、宠物是否在场）在两代之间都不可比。

另有一份 `0001.mwr` 连 `name` 都不同：名字前多一个 1B 长度（其余文件是 C 字符串）。

所以导出脚本改成**先判代际、再解帧**（`detect_layout`）：整份录像出现过 `0x80` 判 new、
只出现 `0x01` 判 old，然后按对应位读 allied、按需剥长度前缀。两代都解出来的结果
在 `era` 列里标着，跨代统计时按它分组即可——不必把 118 份旧文件整份丢掉。

### 5.6 导出的边界：`.mwr` 里只有战斗帧

137 份录像加起来只出现 **10 个 opcode**（112/113/114/115/116/117/119/122/123/125），
因为录制逻辑是 `net.py:OnServerCmd` 里的 `if f & 2: WriteRecordFile()`，带该 flag 的全是战斗帧。

这意味着**这套语料无法校验非战斗覆盖表**（地图 / NPC / 物品 / 打开 UI 那些）。
那些帧的线序只能靠客户端源码 + `tests/_test_tap.py` 的合成 payload 验，别指望录像能作证。

这 8 个模块占了 111/168 —— 模拟服要覆盖的「主干」，其实就是这 8 个。

### 6.1 这一批补了什么，以及为什么要先改解码器

补的 15 条：`22/25/26/162/164/179/190`（nethero）+ `85/98/99/100/101/102/106/171`（netmap）。
其中 `99` 是**修**不是补——它原来写着 `desc:s`，而客户端读的是 `prop.UnpackDesc`（标签联合），
只有 desc 为空时才「碰巧」是 1 字节 `\0`；`title_len>0` 时还会漏掉一个 title 字段。

为此给 DSL 加了三个原语（`tap.py`）：

| 原语 | 含义 | 用在哪 |
|---|---|---|
| `desc:D` | `UnpackDesc` 标签联合：1B 条目数 + [1B 标签 + N 字节]，N 由 `_DESC_TAG_LEN` 给 | 98/99/106 |
| `title:P(title_len)` | 定长串，宽度取**前面某个字段的值**（`title_len=0` 时吃 0 字节） | 99/98 |
| `bf:B(allied=7,type=6,child=5)` | 1 字节拆多个位（位号=二进制位号，bit7 即 0x80）；原始字节另占一行 | 115 |

`bf` 是补得最晚的一个，但它的缺位一直很难看：`WarAdd(115)` 原来把整个字节命名为 `allied`，
调试台里「我方」显示成 `allied=128`。实际客户端读的是 `UnpackBit(0,1)/(1,1)/(2,1)`，
即 bit7/bit6/bit5 ——**和 WState 同一条 MSB-first 规则**，只是这个字段当年没跟着改。

另有 4 条靠 `_OV_DYN` 按帧内容分流，因为静态规格会「碰巧吃满但读错字段」：

- `85 MapDel`：`len==8` 是清区域（8×1B），否则是删对象（id 4B）。
- `101 NpcSign`：`sub=1` 图标 / `sub=2` 需求物品。
- `102 MapEffect`：**mode 0 / 1-3 / 4 总长都是 7B**，字段却分别是 `tid+eid` / `x+y+eid` / `tid+hp`；不分流就会把 hp 读成 eid。
- `164 NotifyExt`：`itype=6` 是 4×4B 造型四元组，否则单个 4B。

回归：`tests/_test_tap.py` 新增「C3. nethero/netmap 高频帧」24 例，按客户端 `Unpack` 顺序手工合成 payload，
断言「恰好吃满 + 字段名逐项对齐」，并单独验了 desc 的标签解与 MapEffect 的 mode 分流。
