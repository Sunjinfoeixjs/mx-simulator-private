# 详情面板线序抽取（op 144 / 145 / 156）

> 来源：客户端 `src/nethero.py`、`src/netpet.py`、`src/pet.py` 的真实 `Pack*` / `Unpack*` 调用序列；
> 与 `服务端源码/sim/tap.py` 的 `_OV_S2C` 覆盖表逐字段对账。
> 抽取口径与 `_extract_wire.py` 一致（Unpack 调用序列 = 线序权威来源）。

## 0. 请求 ↔ 回包路由（关键：三个 C2S 上行 opcode 的回包不在同一个 opcode）

| 上行 op | 上行函数 | 回包 S2C op | 回包处理函数 | 所在模块（NET_FUNCTION_NAME 路由确认） |
|--------|---------|------------|-------------|----------------------------------------|
| 144 `C2S_GETINFO_SUMMON`  | `nethero.C2SGetSummonInfo`   | **48** `S2CSummonInfo`  | `netpet.S2CSummonInfo`  → `pet.UpdateInfo` | `netpet` |
| 145 `C2S_GETINFO_ITEM`     | `nethero.C2SGetItemInfo`     | **162** `S2CItemInfo`    | `nethero.S2CItemInfo`    | `nethero` |
| 156 `C2S_GETITEMINFOEXT`   | `nethero.C2SGETITEMINFOEXT`  | **190** `S2CItemTCInfo`  | `nethero.S2CItemTCInfo`  | `nethero` |

> ⚠️ 三个上行 opcode 在 `NET_FUNCTION_NAME` 里**另有归属**（144/145/156 被 `netnpc` 占作
> `S2CNpcChat`/`S2CNpcItemChoose`/`S2CNpcItemBill`）。那批是 NPC 对话分支，**不是**详情面板回包。
> 详情面板回包用的是 48 / 162 / 190，二者 opcode 空间不冲突，不要混淆。

## 1. op 144 — 宠物详情（C2S_GETINFO_SUMMON）

### 1.1 上行（C2S，客户端发包）
`nethero.C2SGetSummonInfo(tid, oid)`：
```
[opcode=144 1B][N=8 1B]  tid:4  oid:4
```
线序：`PacketAddI(tid,4)` → `PacketAddI(oid,4)`。定长 8 字节，无分支。

### 1.2 下行（S2C op48，客户端解包）
**线序被拆在三个函数 + 一个循环里**，静态抽取器只看 `netpet.S2CSummonInfo` 会误判为
「委托 helper、无法核对」。真实线序须沿调用链追：

`netpet.S2CSummonInfo` → `pet.UpdateInfo` → `pet.UpdateProp` → `BASE_PROP[4:]` 循环

```
pid:4            UnpackInt(4)                         pet.UpdateInfo
name:20          UnpackString(20)  定长20B GBK+\0    pet.UpdateInfo
shape:2          UnpackInt(2)                         pet.UpdateInfo
desc:D           UnpackDesc(netobj) 标签联合（变长）   pet.UpdateInfo
grade:1          BASE_PROP[4]  TBYTE                  pet.UpdateProp 循环
hp:4             BASE_PROP[5]  TDWORD                 （同时写 m_HPMax）
mp:4             BASE_PROP[6]  TDWORD                 （同时写 m_MPMax）
fp:4             BASE_PROP[7]  TDWORD                 （同时写 m_FPMax）
hpmax:4          BASE_PROP[8]  TDWORD                 （同时写回 m_HP）
mpmax:4          BASE_PROP[9]  TDWORD                 （同时写回 m_MP）
fpmax:4          BASE_PROP[10] TDWORD                 （同时写回 m_FP）
damage:4         BASE_PROP[11] TDWORD
defense:4        BASE_PROP[12] TDWORD
speed:4          BASE_PROP[13] TDWORD
magdef:4         BASE_PROP[14] TDWORD
str:2            BASE_PROP[15] TWORD
con:2            BASE_PROP[16] TWORD
mag:2            BASE_PROP[17] TWORD
cha:2            BASE_PROP[18] TWORD
dex:2            BASE_PROP[19] TWORD
point:2          BASE_PROP[20] TWORD
exp:4            BASE_PROP[21] TDWORD
expnext:4        BASE_PROP[22] TDWORD
expneed:4        BASE_PROP[23] TDWORD
life:4           BASE_PROP[24] TDWORD（CLifePropItem，≥64000 显示「永生」）
molingguo:1      BASE_PROP[25] TBYTE
```
- `BASE_PROP[0..3]`（m_Name / m_Shape / m_Desc / m_AttackType）**不在线上**：前三个由
  `UpdateInfo` 直接读，第四个 `m_AttackType` 由 `petdata.GetData(shape)['attack_type']` 本地派生。
- `shape==65535` 是**解包之后**的删除分支（不影响字节流），线序恒为线性。
- `BASE_PROP[5..10]` 的 `BindPropMultiItemText` 一个 4B 读数同时写「当前值 + 上限值」两组
  属性——这正是 2026-10-18 真机修正（残血进战斗不再显示 170/170）的根因。

### 1.3 对账（覆盖表 op48）
覆盖表现状：`48: ('S2CSummonInfo', 'pid:4 name:f20 shape:2 desc:s grade:1 hp:4 mp:4 fp:4 hpmax:4 mpmax:4 fpmax:4 damage:4 defense:4 speed:4 magdef:4 str:2 con:2 mag:2 cha:2 dex:2 point:2 exp:4 expnext:4 expneed:4 life:4 molingguo:1')`

| 项 | 结论 |
|----|------|
| 字段顺序 / 宽度 | ✅ 与客户端 `BASE_PROP[4:]` + 服务端 `build_pet_info` **完全一致** |
| `desc` 编码 | ⚠️ **MISMATCH（编码类型）**：覆盖表写 `desc:s`（C 字符串），但客户端读 `UnpackDesc`、服务端 `build_pet_info` 也按 `UnpackDesc n=0`（单字节 `0x00`）打包。空 desc 时两者恰巧重合（都是读到 `\0` 即止），**但 desc 非空时 `s` 与 `D` 解码会错位**。 |

**修复建议**：覆盖表 `desc:s` → `desc:D`，并补 `_OV_NOTE[48] = 'desc 是 UnpackDesc 标签联合（不是 C 字符串），与 op98/99/106 同'`。
（空 desc 场景下调试台不报错，是这个 bug 一直没暴露的原因——和 `SceneM(96)` 同一类「静默错位」。）

## 2. op 145 — 物品详情（C2S_GETINFO_ITEM）

### 2.1 上行（C2S）
`nethero.C2SGetItemInfo(tid, oid)`：
```
[opcode=145 1B][N=8 1B]  tid:4  oid:4
```

### 2.2 下行（S2C op162，`nethero.S2CItemInfo`）—— 干净线性，无分支无循环
```
itype:1   UnpackInt(1)
key:2     UnpackInt(2)
id:4      UnpackInt(4)
ext:s     UnpackString(0)   变长 GBK C 串，直到 \0
```
`ext` 是结构化物品详情的「外壳」：函数把 `ext` 交给 `dlggetinfo.UpdateServerItemInfo(itype,id,key,ext)`
二次解析，**线上边界就是 `ext:s` 这一段**。

### 2.3 对账（覆盖表 op162）
覆盖表：`162: ('S2CItemInfo', 'itype:1 key:2 id:4 ext:s')`
✅ **逐字段完全一致**（类型 + 宽度 + 变长边界）。无需改动。

## 3. op 156 — 物品附加信息（C2S_GETITEMINFOEXT）

### 3.1 上行（C2S，含 subtype 分支）
`nethero.C2SGETITEMINFOEXT(id, id1)`（另有 `C2SGETSPIRITBALL` / `C2SGETWARINFO` 复用同一 opcode，仅首字节不同）：
```
[opcode=156 1B][N=9 1B]  subtype:1  id:4  id1:4
```
- subtype=1 → 物品附加信息（`C2SGETITEMINFOEXT`）
- subtype=2 → 灵兽球（`C2SGETSPIRITBALL`）
- subtype=3 → 战况信息（`C2SGETWARINFO`）

### 3.2 下行（S2C op190，`nethero.S2CItemTCInfo`）—— 干净线性，无分支无循环
```
itype:1   UnpackInt(1)
key:2     UnpackInt(2)
id:4      UnpackInt(4)
ext:s     UnpackString(0)   变长 GBK C 串，交给 dlggetinfo.UpdateTradeCenterItemInfo
```

### 3.3 对账（覆盖表 op190）
覆盖表：`190: ('S2CItemTCInfo', 'itype:1 key:2 id:4 ext:s')`
✅ **逐字段完全一致**。无需改动。

## 4. 对账结论汇总

| op | 回包 | 线序来源 | 与覆盖表 | 备注 |
|----|------|---------|---------|------|
| 144 | 48 `S2CSummonInfo` | `netpet`+`pet.UpdateInfo/UpdateProp/BASE_PROP[4:]` | ⚠️ `desc:s`→`desc:D` | 拆 3 函数 + 循环，静态抽取器需扩展才能自动核对 |
| 145 | 162 `S2CItemInfo`   | `nethero.S2CItemInfo` | ✅ 完全一致 | 干净线性 |
| 156 | 190 `S2CItemTCInfo` | `nethero.S2CItemTCInfo` | ✅ 完全一致 | 干净线性 |

**唯一需改的覆盖表项：op48 的 `desc:s` → `desc:D`**（与 op98/99/106 的 `_OV_NOTE` 惯例统一）。
