## 2. 随机源收口

### 2.1 12 处调用 → 11 条流

| 原调用 | 位置 | 新流 |
|---|---|---|
| `random.choice(_enc['monsters'])` | `_start_war` 遇怪选怪 | `encounter` |
| `random.random() < pas['combo_chance']` | 宠物连击 | `combo` |
| `random.random() < pas['crit_add']` | 宠物会心 | `crit` |
| `random.random() >= DROP_CHANCE` | 掉落触发 | `drop` |
| `random.choice(pool['pools'])` | 掉落池挑选 | `drop_pick` |
| `random.choice(items)` | 掉落条目挑选 | `drop_pick` |
| `random.choice(targets)` | 敌方选目标 | `enemy_target` |
| `random.random() < self.enemy_skill_chance` | 敌方放不放招 | `enemy_skill` |
| `random.choice(self.enemy_skills)` | 敌方挑招 | `enemy_pick` |
| `random.random() < self._hurt_bs_chance` | 敌方会心 | `enemy_hurt` |
| `random.random() < rate`（×2 处） | 逃跑判定 | `escape` |

**为什么要分流而不是一个流**：全局单流下，「多触发一次掉落判定」会把后面
「敌方打谁」的随机数挤走 —— 于是「关掉掉落」这样一个无关改动，会让敌方行为
整体换一套。分流后每条用途独立，改 A 不影响 B（不变量 I2，有断言）。

**为什么 `chance(0)` / `chance(1)` 不抽随机数**：必然事件不该推动随机序列。
这不只是省事 —— 如果必然事件也抽，那么「把某个概率从 0 调成 1」会连带改变
后续所有流的取值，排查时极难解释。同理，`choice()` 在只有一个候选时也不抽。

### 2.2 每场重置

`begin_battle()` 用 `_mix32(主种子, 场次 × 0x9E3779B1)` 派生本场种子并清空所有流。
不这么做的后果：第 1 场掉过一次装备，后面每场的随机序列都被那次历史挤了位，
「同种子重跑整局」对不上。

`_mix32` 用 FNV-1a 而不是内置 `hash()`：字符串 hash 在 Python 3 里带**进程级
随机化**，同一流名在不同进程会派生出不同种子，「跨进程可复现」直接没了。

### 2.3 可退化

`battle_rng.enabled = False` 时退化为直通模块级 `random`（不变量 I4）。
切换会清空已有流 —— 一边用独立流抽了一半、一边又用全局流，状态对不上会得到
「既不是 A 也不是 B」的第三套序列。

## 3. 状态效果

### 3.1 数据：284 条真值怎么来的

客户端 `src/data/buffdata.py` 是反编译产物，两个顶层表：

```python
DATA = {10: {'desc': b'\xb7\xb4\xbb\xf7\xa3\xbb...'}, ...}   # 284 条
ICONTABLE = {46: 236, 526: 264, ...}                          # 249 条
```

`desc` 是 **GBK 字节串**，直接 grep 中文搜不到、当 utf-8 读是乱码。283 条走
`b'...'` 字面量，唯独 **145 号**被反编译器写成了 str（`'\u04ba\u032c'` ——
GBK 的 `D2 BA CC AC`），需要 `encode('utf-8')` 再 gbk。两条路径都得走，
漏一条就少一条状态。

### 3.2 证据分级：能算什么，不能算什么

| 层级 | 数量 | 说明 |
|---|---|---|
| 状态 id / 名字 / 说明 | **284** | TRUE —— 客户端直读 |
| 说明里带 ASCII 数字 | **34** | 候选，不等于可机读 |
| 可转录成修正 | **29** | PARTIAL —— 从**说明文字**转录，逐条带 `src` 抄下原文 |
| 有数字但不可转录 | 5 | UNKNOWN —— 等级门槛（24/41）/ 只说「降低」无数值（235/253）/ 解除条件（282） |
| 另有登记 | 1 | 25 号原文无数字（「终级隐身…除非攻击者拥有感知能力」），与 24 同族，一并登记以免隐身族残缺 |
| 整片无数字 | 250 | UNKNOWN —— 如 20「燃烧；…每回合对承受者造成伤害」，连百分比都没写 |

**为什么标 PARTIAL 而不是 TRUE**：数值是从**玩家可见的说明文字**里读出来的，
不是从参数表读出来的。说明写「每回合掉当前气血上限的20%」，我就按 20% 算 ——
这可能有出入（实际参数可能 0.2、可能经过等级缩放），但至少有出处、可回溯。
逐条 `src` 字段就是为此存在的。

**「大幅度提高」怎么办**：不编。157「三花聚顶；法术伤害结果大幅度提高，持续6回合」
只转录 `turns=6`，倍率留空。同理 418/419（神力/坚盾）原文是「修炼 +10」，
而本服没有修炼表，所以 `atk_mul`/`def_mul` 都写成 1.0（中性）而不是臆造倍率。

### 3.3 机制

`EffectSet` 按**单位**分表（主角 / 宠物 / 每只敌方各一个）。全局单表会让
「敌方身上的燃烧」与「主角身上的燃烧」共用计时，tick 一次两边一起掉。

叠加规则来自转录表的 `stack` 字段：

| 模式 | 语义 | 例子 |
|---|---|---|
| `refresh`（默认） | 已有则续时长，**不叠层**；时长取「现有与新值中较大者」 | 184 狂暴 |
| `add` | 层数累加 | 279 溺水（desc「可叠加4次」）、403 野性 |
| `ignore` | 已有则完全不动 | —（预留） |

**溺水 279 单独收口**：desc 说「每回合开始时减少20％，效果可叠加4次（**用加法叠加**，
也就是说这几样属性最低可被减至20%）」。加法叠加后取剩余（1 - 0.2×层），
与其它乘区的语义不同，混在 `_MUL_KEYS` 里会算错。

**乘区聚合**（本服约定，C 级）：乘区逐项相乘，加法逐项相加，标志任一为真即真。
两个不同状态 +20% / -20% 法伤 → ×0.96，不是 ×1.0。原文没写多状态如何叠加。

### 3.4 与现有战斗的接入（关键：默认零影响）

| 接入点 | 位置 | 默认（无状态）行为 |
|---|---|---|
| 承伤修正 `_fx_taken` | `_enemy_attack` 打主角/宠物 | **原值返回**（同一个整数），录像复现值 50/48/20 逐位不变 |
| 强制防御 `_fx_force_defend` | 同上 | `False`，走原逻辑 |
| 回合末 DOT + 计时 `_fx_end_of_round` | `_resolve_hero_round` / `_finish_pet_turn` 收口 | **零帧**（不发任何帧） |

「默认零影响」是硬要求：录像复现帧序列被多处逐帧断言，接入只要动了一帧就会炸。

### 3.5 已知缺口

- **敌方 DOT 只扣血、不发帧**：客户端对敌对单位没有 HPPercent 通道（会画错血条），
  敌方血条只在 WarDel 时才更新。所以敌方被 DOT 打死时血条是「突然消失」。
- **敌方受伤不走 `taken_mul`**：敌方伤害结算在 `_damage_frames` 里，本轮没接
  （改动面大、风险高）。主角/宠物受伤已接。
- **修炼类加成未换算**：403 野性（每次受击 +2 级修炼）、418 神力、419 坚盾、
  41 冥界波都要修炼表，本服没有。只记层数，不折算属性。
- **无施加方式**：状态的「谁在什么条件下挂上」不可得（buffdata 没有这个字段）。
  当前只能通过 GM 指令施加。

## 4. 敌方 AI

原来四个判断直接写在 `_enemy_attack()` 的 40 行帧编排中间。抽成两个纯函数：

```python
tgt = eai.pick_target(rng, targets, policy, hp_ratio)      # 选目标
protector = self._round_protectors.pop(tgt, None)          # 查保护（要 pop，有副作用）
dec = eai.decide_action(rng, skill_chance, skills, hurt_chance,
                        protected=has_protect)             # 放不放招/哪招/会心
```

**为什么不塞进一个 `decide()`**：保护关系要先知道「打谁」才能查，而「是否放
技能」又依赖「有没有发生保护」。顺序天然是 选目标 → 查保护 → 决定动作，
硬塞进一个函数只能变成回调或**重复抽取** —— 后者会让随机消耗翻倍，同种子复现
直接失效。（初版就是这么写的，被自己的测试抓到：`enemy_pick` 抽了 2 次。）

抽取顺序与原实现一致（不变量 I1）：`target → skill_chance → skill_pick → hurt`，
一样不多、一样不少。保护触发时**仍然掷「是否放招」再否决** —— 不是直接跳过，
否则随机消耗就比原来少一次。

两种策略：

| 策略 | 行为 | 用途 |
|---|---|---|
| `random`（默认） | 存活友方里等概率选 | **逐位复刻既有行为**，不是新行为 |
| `focus` | 气血比例最低者优先，并列取靠前的 | 验证「策略可替换」确实成立 |

`focus` **不消耗** `enemy_target` 流：策略本身是确定性的；这里若掷一次骰，
后续所有流的序列都会跟着漂，「集火」这个只是换个目标的策略会顺手改掉会心/
掉落的运气，排查时极难解释。

`explain()` 能把决策翻成一句人话（「打 宠物 放招式 415 会心」），
`_last_enemy_decision` 留档，GM 可查。

## 5. 胜负只结算一次

原有 `_after_hero_action` 已有 `if not self.in_war: return True` 幂等守卫。
但守卫只挡得住「已经收尾之后的重复调用」，挡不住「同一批死亡单位在收尾**过程中**
被二次结算」。所以加了显式计数：

```python
self._war_settle_count   # 本场结算次数，正常必须 ≤1
self._war_settle_kinds   # ['win'] / ['lose'] / ['escape'] ...
```

重复结算会打 warn 日志 + 调用栈前 3 层，能直接定位是哪条路径在重入。

**顺带修掉一个真 bug**：`_after_hero_action` 原来在循环里逐只调 `_on_enemy_dead()`，
一次全灭 3 只就发 **3 遍 TaskAdd** + 落盘 3 次。改成先全部 WarDel、再统一推进
（`_on_enemies_dead(conn, n)`）：

- **帧序不变**：WarDel 仍逐只 3 帧（有断言）
- **进度语义不变**：每只 +1
- **TaskAdd 收敛 1 次**、落盘 1 次

**另一个真 bug**：`dead_ids` 里若有重复或已死的 id，旧实现照样推一格任务进度
（等于凭空多加）。现在只算真正从 `enemy_hp` 里 pop 掉的。

六路入口都测了结算次数：普攻全灭 / 3 只同灭 / GM win / 战败 / 逃跑成功 / 收尾后重入。

### 6.1 顺带修掉的三处测试打桩（必须披露）

改随机源后，三个既有测试红了。**没有改任何一条断言**，改的是「怎么让概率生效」：

| 文件 | 原做法 | 新做法 | 为什么原做法不对 |
|---|---|---|---|
| `_test_pet_skill.py` | `mock.patch.object(m.random, 'random', side_effect=[0.99, 0.01])` | `mock.patch.object(s3, '_pet_passives', return_value={...crit_add: 1.0})` | 打桩的是**实现细节**（模块级 random），不是行为。而且它钉的是「第 1 次抽 0.99、第 2 次抽 0.01」这种脆弱顺序 |
| `_test_common_ops.py`（8 处） | `mock.patch.object(m.random, 'choice', side_effect=lambda values: values[0])` | `mock.patch.object(srv.battle_rng, 'choice', side_effect=lambda name, seq: seq[0])` | 同上；新写法还顺带暴露了「取第几个候选」这个真实意图 |
| `_test_state_consistency.py` | `random.seed(12345)` + `random.getstate()/setstate()` | `srv.battle_rng.reset(12345)` + `state()/restore()` | `random.seed()` 已经管不着战斗了 —— 不换的话这段会变成「运气好才过」的 flaky 测试 |

改后三处全绿，且断言的**语义**比原来更清楚：「必杀必触发」现在由
`crit_add=1.0` 这个**语义参数**保证，而不是靠「第二次抽到 0.01」。

### 6.2 测试抓到自己刚写的 bug

初版 `_enemy_attack` 里我写了：

```python
_pre = eai.decide(self.battle_rng, targets, 0.0, (), 0.0, ...)   # 先选目标
tgt = _pre['target']
protector = self._round_protectors.pop(tgt, None)
dec = eai.decide(self.battle_rng, [tgt], ..., policy=P_FOCUS if False else P_RANDOM, ...)
```

两个问题：① **调了两次 `decide`**，随机抽取翻倍；② `policy=eai.P_FOCUS if False
else eai.P_RANDOM` 是纯垃圾（等于常量）。测试 `assert enemy_pick 抽了 1 次`
直接判红，才看出来。改成 `pick_target()` + `decide_action()` 两步式。

### 7.0 后补的两条变异（2026-10-23 补测，因为发现了转录层的漏洞）

第 6、7 条是后补的。起因：原有断言只查 `src` **非空**，
拦不住「把 30% 抄成 35% 但 `src` 照样写着一句话」——而「不得伪造真值」
是 P3 指令的硬约束，靠「作者自觉」守不住。补了 5 条断言（101 → 106）：

| 断言 | 守什么 | 能否被绕过 |
|---|---|---|
| `src` 引号内**每一段**（省略号切段后）都是客户端说明的逐字子串 | 转录不许编、不许抄错 | 不能：改数字/改措辞立刻不是子串 |
| `QUANT_CANDIDATES` **恰好等于**「说明里含阿拉伯数字」的集合（双向 34↔34） | 清单不许漏（漏一条 = 少做一条能做的活，报告却显得老实） | 不能：单向子集检查会漏，故用双向 |
| 建模条目 ⊆ 可量化清单 | 不许绕过清单直接建模 | 不能 |
| 建模 ∩ 不可读 = ∅ | 一条状态不许既建模又声称读不出 | 不能 |
| 6 条不可读都带「—— 理由」且够具体 | 不许把「懒得做」写成「读不出」 | 不能：删理由立刻红 |

> 变 6 实测：`[FAIL] [(165, 'not_verbatim', '使用治疗或复活类法术的效果提高35%')]` —— 精确定位到条与段。
> 变 7 实测：`[FAIL] [(235, 'no_reason', '天罗地网符')]`。

> 但那个包含关系只是**当前数据的巧合**，不是不变量（本来就无数值的状态登记为
> 不可读是合理的）。这种「编码了巧合」的断言比没有更糟——将来会误伤正当改动。

### 7.1 头一轮有两个变异打不红（必须披露）

第一次跑变异，**M2 和 M5 都还是绿的**。不是变异构造错了，是**测试有覆盖漏洞**：

| 变异 | 为什么没打红 | 补了什么断言 |
|---|---|---|
| M2 `taken_mul` 相乘→覆盖 | 测试只挂了**一个** `taken_mul` 状态（水晶墙 ×0.2）。只有一个时「相乘」和「覆盖」结果相同，测不出来 | 加「188 水晶墙 + 260 最终诅咒同时挂 → 0.20×1.15=0.23」 |
| M5 去掉进度上限钳制 | 测的是 `progress=0` 加 3 只，而 `TASK_NEWBIE_NEED=3` —— `min(3,3)` 与 `3` 相同，`min()` 有没有都一样 | 改成从 `NEED-1` 起、一次加 5 点，必须停在 `NEED` |

补断言后两个变异都判红（断言数 98 → 101）。**这两条不是「为了让变异变红而硬凑」**：
「两个减伤状态同时挂要相乘」和「进度不能冲过任务上限」本身就是该守住的行为，
只是原来漏了。

## 9. 已知问题与剩余风险

1. **敌方 DOT 血条不同步**（§3.5）—— 敌方被 DOT 打死时客户端血条是「突然消失」。
   要修得先解决「敌方单位没有 HPPercent 通道」这个协议限制。
2. **敌方受伤不走 `taken_mul`** —— 水晶墙之类的减伤只对主角/宠物生效。
3. **状态无法被战斗正常施加** —— 只有 GM 能挂。因为「什么招式附带什么状态」
   在客户端数据里没有映射（`petskill` 只有 type/desc，没有状态 id）。

   被施加也没有任何战斗效果（只有名字和说明）。
5. **`focus` 策略未经真实战斗验证** —— 只测了「选目标」这一层，没有跑完整场
   战斗看它是否会造成难以取胜的局面。
6. **`battle_rng` 的 `escape` 流与其他流隔离** —— 逃跑判定现在不影响其它流，
   这是改进；但如果原服逃跑失败与后续行动有相关性（例如「失败后更容易被杀」），
   本服复现不出来。
