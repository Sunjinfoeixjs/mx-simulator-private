## 0. 先说结论（避免误判进度）

上一轮（P3-01 报告 §9）给过结论：「宠物属性不需要重写，现状两层已对」。本轮**维持**
这个判断，但做了三件当时没做的事：

1. **把三层合成从 `m4_server` 里搬出来**成一个纯函数模块 `pet_progression`，
   让「这只宠物强在哪一层、加点贡献多少」可以被单独问出来（P3-07 的诊断要用）。
   这是**搬家 + 收口**，不是重写：默认宠物逐位仍是录像读数（回归第 ② 组守着）。
2. **补上宠物技能的真值数据**。原来本服只有一个 6 元素常量 `PET_SKILLS` 和两条
   手写 desc 断言，「宠物能学什么」根本没有依据。本轮从客户端 `petskill.DATA`
   生成 **404 条**技能表，于是「学什么合法」「这个技能叫什么」第一次有了出处。
3. **把技能表的增删做成服务**（`pet_skill_service`），带白名单、绑定 id 归一、
   去重、上限、遗忘、替换，且失败零副作用。

**没有做的**：召唤兽装备的数值效果（真值不可得）、魔兽要诀→技能的映射
（数据不存在）、资质洗练（客户端无入口）。三条都标 `blocked` / `not_implemented`，
不写假数值。

### 6.1 顺带修掉的既有测试缺陷：假技能 id（必须披露）

`_test_pet_instance` 原来用 `1001` / `1002` 当「新学的技能」。这两个 id **不在**
客户端 `petskill.DATA` 里——它们来自 `battle_formulas.PET_SKILL_DATA` 那张
早期手编的 28 条表（1001..1068，与真表的 101..530 + 4xxx/45xxx 完全不重叠）。
加上白名单校验后它们会被判 `unknown_skill`，所以改成真表里的 `101 反击` / `103 魔法反击`。

> 这是**修正假数据**，不是放宽断言：原断言「学会后 op49 里有它」一个字没改。
> 同时也说明了一个副作用——`battle_formulas.PET_SKILL_DATA` 与客户端真表不相交，
> 以后不要拿它当宠物技能的白名单（本轮改用 `pet_skill_data`）。

### 6.2 测试抓到了自己刚写的 bug

第一次跑第 ⑧ 组时判红：「手工调高的资质不被压回等级值 ← `{3:3, 4:3, ...}`」。
原因是新写的 `normalize_attr_lv` 只认 int 键，输入是 `{'3': 9, ...}` 时取不到，
默认 1 再 `max(1, level=3)` → 9 被静默吞掉。修法是两种键都认（`attr.get(i, attr.get(str(i), 1))`）。

> 记这一笔是因为它正好是「收口」这类重构最容易引入的回归：行为看起来没变，
> 只在**手改档 / 存档 JSON** 这种边上才露出来。

## 7. 变异验证（4 个有效变异，全部判红，还原后全绿）

| 注入的缺陷 | 判红项 | 为什么该红 |
|---|---|---|
| `POINT_EFFECT['con']` 10 → 11 | 1 项（体质 +4 → 面板 hp +40） | 加点换算错 1/点，面板直接 +44 |
| `ids_of` 不做绑定归一（`10415` 不折成 `415`） | 2 项（归一结果 / 「已有该技能」） | 绑定技能会被当成第二个技能重复占格 |
| 白名单校验 `if False and ...` | 2 项（unknown_skill / 拒收后零变化） | 表外 id 被收下，客户端显示 `未知<id>` |
| `normalize_attr_lv` 改成「已达标项每次 +1」 | 11 项（默认宠物 = 参考宠 / 战斗层 / 资源层 / 资质五项 …） | 资质不再幂等，×1.0 锚当场破 |

还原后 `diff` 与备份逐字节一致，重跑 80/80 全绿。
