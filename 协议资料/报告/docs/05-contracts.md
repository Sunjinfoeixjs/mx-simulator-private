### 4.2 `_dispatch`：顺序即契约

`_dispatch`是一条**从上到下第一个命中即生效**的长 `if/elif`，
链尾 `elif self.in_war:` 是战斗保底（回一帧 `WarTurn` 推回合）。

> **插入位置比代码本身更重要**。客户端在战斗中**也会**发 OPENUI / COMMON / 用道具 /
> 上报点击统计，这些一旦落到保底，就会凭空多回一帧 `WarTurn`，把回合推给敌方

## 14. 全链路硬约束清单（改代码前必读）

| # | 约束 | 违反后的现象 |
|---:|---|---|
| 1 | C2S `[op][len]`、S2C `[len][op]` | 整条连接失步 |
| 2 | 25B 握手是裸区 | 首字节被当长度，C2S 全吞 |
| 3 | 变长串 = GBK + `\0`，无长度前缀 | 名字前出现「口」、越界读吞后续帧 |
| 4 | 定长串补齐（20/26） | 字段错位 |
| 5 | `SceneM` 会清空场景 → 必须补 `AddNpc`+`GotoM` | 地图全空 |
| 6 | `WarEnd` 会清空场景 → 必须 `_resync_scene` | 回到场景无对象、请等待残留 |
| 7 | `WarTurn` 是回合推进唯一开关 | `g_Turn==0` 时攻击演出被忽略 |
| 8 | 每场只发一次 `WarStart` | `g_WarTimes` 累积，`WarEnd` 被丢弃 |
| 9 | `WState` 位域 MSB-first；`allied` 在 bit7 | 单位阵营错、受伤表现错 |
| 10 | `hp_chg` 正数 = 扣血 | 伤害被当回血 |
| 11 | 招式必须回 `WarPerform(122)` | 放完招式卡「请等待」 |
| 12 | `HPPercent(125)` 只对友方 | 敌方无血条对象 → `AttributeError` |
| 13 | 战斗中的非战斗帧必须排在保底之前 | 凭空多推一帧 `WarTurn` |
| 14 | 宠物指令是第二段异步包 | 不挂起就推进回合 → 卡指令 |
| 15 | 148 第一列是 `shape`；卖出带列表下标 | 卖错物品 / 面板名错 |
| 16 | 主角战斗 id 必须非 0 | 指令菜单不出现、点敌人无反应 |
| 17 | 经验/掉落必须在 `WarEnd` + `_resync_scene` **之后**发（顺序：`WarEnd` → `_resync_scene` → `_award_battle_exp` → `_roll_drops`） | 经验/物品被客户端场景重建冲掉 |
| 18 | 所有主角动作入口第一句必须是 `_accept_turn()` | 一次操作被结算两次 / 已结束的战斗仍在扣资源 |
| 19 | 所有「战斗结束」路径必须经过 `_reset_war_state()` | 下一场白挨一轮、自带防御/保护、首次行动被吞、宠物窗口串台 |
| 20 | 非法指令只回 `WarTurn(0)` 重开窗口，**不消耗回合**；合法但无演出的指令必须走 `_resolve_hero_round` | 前者=点错一次白送敌方一轮；后者=敌方不动、回合不推进 |
| 21 | 合批层必须在抓包器**下面**；任何阻塞读之前必须 flush；非分派路径的推送要显式 `_flush_out()` | 抓包缺帧 / 客户端读阻塞 / GM 按钮「点了没反应」 |
| 22 | 战斗帧字段只在 `frames.SPEC` 里定义，收发与调试台解码都从它派生 | 三份定义各自漂移（166 条件字段、169 缺 id、115/123 位序都错过） |
| 23 | 宠物招式/被动未登记效果一律**回落普攻并写明原因**，不许「假装有」 | 玩家看到招式动画、实际打的是普攻伤害 |

### 14.1 现象倒查表

上表是「改代码前必读」，这张是它的**反向索引**：先看到现象，再定位是哪条约束被破。

| 现象 | 违反的约束 | 查哪里 | 怎么验 |
|---|---|---|---|
| **地图全空** | #5：`SceneM` 后没补 `AddNpc` + `GotoM` | `_send_scene` 是否三连完整 | tap 帧流里 `SceneM` 后 500ms 内是否有 `AddNpc` |
| **战斗菜单不出现** | #16：主角 war id 为 0 | `_start_war` 的 `HERO_WAR_ID` | tap 里 `WarAdd` 帧 id 字段 |
| **打了怪没经验** | #17：经验必须在 `WarEnd` + resync 之后 | `_award_battle_exp` 调用点（应在 `_resync_scene` 之后） | 帧流顺序 `WarEnd` → `SceneM` → `AddNpc` → `GotoM` → `PropChange(exp)` |

> 三条都用同一套方法定位：**看帧流顺序**，而不是猜代码。
> 现象类 bug 的共性是「帧没发 / 发晚了 / 发早了」，tap 里一眼能看出来。
