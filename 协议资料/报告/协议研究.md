## 1. 协议栈总览 —— 四层模型

《梦想世界》的网络协议跨越 **Python 脚本层** 与 **C++ 原生层（mxmain.dll / CNet）** 两界，自底向上可抽象为四层：

```
┌─────────────────────────────────────────────────────────────┐
│ ④ 应用/脚本层  net*.py (44 个 net 模块, ~1194 协议函数)        │
│    C2S_* 语义、S2C_* 处理函数、PacketAddI/AddS 调用序列        │
├─────────────────────────────────────────────────────────────┤
│ ③ 封包层 (原生 CNet)                                          │
│    PacketPrepare / PacketAddI / PacketAddS / PacketSend       │
│    NakedSend / UnpackInt  —— 类型化字段 → 字节流              │
├─────────────────────────────────────────────────────────────┤
│ ② 加密层 (原生 0x43cc50, 状态在 CNet 对象 +0x1090 / +0x80)     │
│    对称 XOR 流密码, 收发双独立状态, +0x72 开关, SetSeed 驱动   │
│    ★ 受 VMProtect 保护 (区段 5006i44r, VA 0x598000)            │
├─────────────────────────────────────────────────────────────┤
│ ① 传输层 (TCP)                                                │
│    Connect 裸发 ip:port (NakedSend, 不加密)                    │
│    Hello 种子交换 (NakedSend 25B, 不加密) → 之后全加密         │
└─────────────────────────────────────────────────────────────┘
```

**关键边界**：`opcode` 与 类型化字段 在 **③封包层 / ④脚本层** 确定（逻辑内容），而 **加密** 完全发生在 **②原生加密层**，在 `PacketSend()` 内部、出网前施加。即「逻辑报文（opcode+字段）」与「密文」是解耦的——这正是自搭环境闭环能成立的根本原因（两端用同一占位 cipher 即锁步一致）。

## 2. 协议字典提取方法

### 2.1 来源与两类「名字」
- **C2S / GS2C opcode**：客户端的整数操作码常量，源自 `net.py` 反汇编文本中 `LOAD_CONST <int>` → `STORE_NAME 'C2S_xxx'` 对的提取。
- **S2C 路由**：服务端→客户端的处理函数注册表，源自 marshal 常量表中 `[module, 'S2Cxxx', tag]` 元组（部分含 `tag` 优先级标记）。

### 2.2 模块归属算法
`enrich_c2s_module.py` 遍历每个 `net*.py` 的 code 树 `co_names`，遇到 `C2S_/GS2C_` 全局名即记为该模块定义；排除中心定义模块 `net` 后，取首个出现的模块；对无特定模块的 opcode 用关键词→模块启发式（`KW_MOD`）兜底。结果：123 个中 5 个回退到 `net`、2 个出现在多模块（`C2S_PLAYER_IB`、`C2S_OPENUI`）。

### 2.3 规模
| 维度 | 数量 |
|---|---|
| C2S/GS2C opcode | 123（其中 C2S_ 120，GS2C_ 3） |
| S2C 路由（处理函数） | 160 |
| opcode 取值范围 | 1 .. 192（中间 71 个空洞，属正常版本演进累积） |

> 战斗 + 角色/属性 + NPC + 宠物 四类合计 61 个（≈一半），是该游戏协议面的核心负载，符合 MMORPG 以「战斗 + 养成 + 交互」为主的内容特征。

### 3.2 关键 opcode 详解（登录链路）
登录链路在「进入游戏 7 步」中已逐字节验证，涉及的 opcode 全部落在 `netlogin`：

| opcode | 名称 | 角色 |
|---|---|---|

| 2 | `C2S_LOGIN_PLAYER_ENTER` | 选角色进入 |
| 3 | `C2S_LOGIN_PLAYER_ADD` | 无角色时建角色 |
| 4 | `C2S_LOGIN_QUEUE` | 排队状态 |
| 8 | `C2S_PING` | 心跳维持（`g_PingTimer` 周期发送） |
| 9 | `C2S_LOGIN_LOCALPW` | 本地密码缓存 |
| 10 | `C2S_RESULT` | 登录结果回执 |
| 14 | `C2S_BACLLIST` | 黑名单/禁言相关 |

### 3.3 编号空间特征
- **范围 1..192，71 个空洞**：非密集分配，说明协议随多版本迭代累积（保留旧 opcode 不回收，新功能向后追加）。
- **3 个 `GS2C_` 常量**（GameServer→Client 方向的 opcode）：客户端侧也持有这些整数常量，表明游戏服→客户端的某些通道同样用整数 opcode 编址，但规模远小于 S2C 路由表——两条方向可能用不同寻址体系（见 §4）。

## 4. S2C 路由面（160 个路由）

### 4.1 与 C2S 的本质区别
C2S 是「**整数 opcode → 处理函数**」；S2C 是「**模块.处理函数 路由表**」，每条路由由 `(module, handler, tag)` 三元组描述。**当前未发现 S2C 使用整数 opcode 寻址**——服务端下发包更可能是 `(路由id/tag, 序列化参数)` 形式，客户端按 `(module, handler)` 查表派发。这解释了为什么 160 个 S2C 处理函数与仅 3 个 GS2C 整数 opcode 数量悬殊。

### 4.2 模块分布（Top）
| 模块 | 路由数 | 模块 | 路由数 |
|---|---|---|---|
| netwar | 22 | netpet | 8 |
| nethero | 21 | netplayer / netitem | 各 7 |
| netmap | 17 | netmail / netliving | 各 4 |
| netnpc | 17 | netchat | 4 |
| netlogin | 11 | nettask / netfriend | 各 3 |
| | | 其余 20+ 模块 | 各 1–2 |

### 4.3 ★ 核心发现：`tag` 是派发优先级 / 子系统分桶标记
160 条路由中 **39 条带 `tag`**，分布如下，且高度按子系统聚类——这是本次研究最重要的新发现：

| tag | 数量 | 全部路由归属 | 语义推断 |
|---|---|---|---|
| **18** | 18 | 全部 `netwar.*`（攻击/回合/HP%/召唤/天气/演出…） | **战斗实时桶**：高频、时序敏感，最高派发优先级 |
| **1** | 11 | `netitem.*`（增删/位置/数量）+ `netpet.*`（状态/召唤信息/技能键） | **物品/宠物状态变更桶**：必须可靠落库的状态同步 |
| **16** | 6 | `netchat.PlayerChat` / `netnpc.NpcChatExt` + `netwar` 播报（战签字/战开场/被召唤宠…） | **战斗播报桶**：聊天式/公告式战斗信息 |
| **19** | 3 | `netchat.Notify/SysNotify` + `nethero.NotifyExt` | **系统通知桶**：滚屏/系统消息 |
| **3** | 1 | `netchat.S2CWarNotify` | 杂项战报（经聊天通道的战斗提示） |
| None | 121 | 登录/地图/好友/任务/邮件等其余全部 | 默认优先级，按到达顺序派发 |

**结论**：`tag` 不是数据字段，而是 **客户端 S2C 派发表的优先级分桶索引**——`18` 战斗走最快路径，`1` 物品/宠物变更优先落状态，`19/16/3` 为各类通知，`None` 为默认。该结论与上一轮对 tag 分布的初步观察（18=战斗、1=物品）完全一致并被 160 条全量数据证实。

### 4.4 子系统分布（路由）
角色/宠物 25、其他 19、地图/移动 19、系统/UI 18、战斗 17、登录/账号 16、物品/仓库 16、社交 10、交易/经济 8、NPC 7、任务/活动 5。

## 5. 登录报文字段布局（已逐字节验证）

来自 `entry_protocol_sim.py` / `login_netlogin_fixed.dis`（186–530 行），`C2S_LOGIN_ACCOUNT_ENTER`（opcode=1）字段序列：

```
PacketPrepare(1)
  PacketAddI(CLIENT_SCRIPT_VERSION[0],1)   # [0,10,43]
  PacketAddI(CLIENT_SCRIPT_VERSION[1],1)
  PacketAddI(CLIENT_SCRIPT_VERSION[2],2)
  PacketAddS(name, 32)                    # 帐号（纯数字约束）
  PacketAddS(pwd, 20)                     # 密码（★明文上总线，仅 6 位）
  PacketAddI ×3 (C_sys.GetVersion 客户端版本)
  PacketAddI ×3 (update.ini [Setting] Version=1.1.50)
  PacketAddI ×4 (本机 IP，OverdoVersion 时伪造 192.168.x.x)
  PacketAddI(adsid>>32,4)+PacketAddI(adsid&0x37FFFFFFF,4)  # 广告 ID 8B
  PacketAddI(len(tgId),1)+PacketAddS(tgId,len)             # 推广 ID
  PacketAddI(driveid,4)                                    # 硬盘序列号
  PacketAddS(mac, len(mac))                               # MAC
PacketSend() → 经 SetSeed 密码加密后入发送队列
```

> **安全观察**：帐号/密码以明文进入逻辑报文，仅靠传输层 XOR 流密码保护；且密码仅 6 位、帐号为纯数字——这是 2013 客户端的历史设计，对今天做私服/协议研究是重要约束。

## 7. 研究结论与下一步

### 已掌握
1. 协议四层模型与「逻辑报文 / 密文」解耦边界；
2. 完整协议字典：123 C2S/GS2C opcode（120+3）+ 160 S2C 路由，含模块归属与子系统分类；
3. S2C `tag` 分桶语义（18战斗/1物品宠物/16播报/19系统/3杂项/None默认）——这是派发优先级标记；
4. 登录链路 opcode 与字段布局逐字节验证。

### 待攻（建议下一步）
1. **`0x43cc50` 真算法**：用 x64dbg/IDA 在 VM 入口 `0x9a26c8` 断点抓 `(seed,明文,密文)` 三元组，拟合真实 LCG/PRNG 常数，替换 `protocol_crypto.RealCipher`；
2. **S2C 寻址机制**：确认服务端下发包是否用整数 opcode 还是 `(module,handler)` 名寻址，补全「服务端→客户端」方向的整数映射；
3. **字段结构补全**：除登录包外，对战斗（netwar）、物品（netitem）、宠物（netpet）等关键 opcode 做字段级逆向，建立「opcode → 字段表」；
4. **`tag` 与 opcode 的对应**：确认 S2C 路由的 `tag` 是否也出现在 C2S 方向，以及 tag 与派发表下标的关系。

*复现/扩展命令：`python extract_protocol.py`（重建字典）、`python enrich_c2s_module.py`（模块归因）、`python gen_listings.py`（生成可读清单）。*
