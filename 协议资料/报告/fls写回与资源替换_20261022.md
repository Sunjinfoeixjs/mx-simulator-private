## 二、无损 FLS 写回

### 2.1 索引加密的逆（`fls_pack.encrypt_entry`）

`fls.py:decrypt_entry` 的解密是：

```
key = i * 0x0E7C83D2
nf3 = f3 ^ (f2 * i * 0xF718FE + 0x0D59D16C)
nf2 = (f0 * f1 + 0x0DF25E) ^ f2
nf1 = (f0 + key) ^ f1
```

注意 `nf3` 的掩码取的是**原始 f2**、`nf2` 的掩码取的是**原始 f1**，所以逆推必须用前一步的**密文**：

```
e0 = p0
e1 = p1 ^ ((p0 + i*0x0E7C83D2) & MASK)
e2 = p2 ^ ((p0 * e1 + 0x0DF25E) & MASK)              # ★ 用 e1
e3 = p3 ^ ((e2 * i * 0xF718FE + 0x0D59D16C) & MASK)  # ★ 用 e2
```

（`dll:FUN_00448c00` 的解密循环与 `fls.py` 一致，见 `fls格式规范.md` §1。）

### 2.2 两种布局

| 布局 | 做法 | 用途 | 判据 |
|---|---|---|---|
| `preserve` | 载荷区**原样拷贝**，索引重加密，表位置不变 | 无损自检、只改索引的场合 | 与磁盘字节**逐字节相同** |
| `compact` | 按索引顺序重排 payload，索引表放末尾 | 替换后长度变化 | 尺寸可精确核算 `12 + Σpayload + N*16 + 表尾` |

### 2.3 实测

```

OK   effect.fls     entries=30   size=234599    compact载荷一致=True 元数据一致=True
OK   skill.fls      entries=282  size=1053288   compact载荷一致=True 元数据一致=True

```

**副产品（对后续替换很重要）**：`war.fls` 的载荷区 `8,381,524 B`，条目合计 `8,339,737 B`
—— 中间有 **41,787 B 空隙**（条目间 padding）。`compact` 会把这些空隙全部丢掉，
所以「替换后整包大小 = 原大小 + delta」**不成立**，只能按 2.2 的公式核算。
客户端按 `f3/f2` 读条目，不依赖空隙（本次未在真机验证这一点，见 §六）。

## 三、`I0` 容器级编解码（`i0.py`）

### 3.1 先分清两种 `49 30`

| 类型 | 结构 | 出现在 | 特征 |
|---|---|---|---|
| 图像 `.res` | `magic(2) ver(2) bpp(2) w(2) h(2) axon(2) ay(2)` + body | war / effect / char 等 | `bpp ∈ {8,15,16,17,…}`，`w,h` 非零 |
| 信息块 | `49 30 01 00` + `count/type` + 变长键值 | **skill.fls 280 条全部是这种** | 按图像头读会得到 `bpp=1` 这种无意义值 |

`i0.looks_like_image()` 用「version==1 且 bpp ∈ 常见集合且 w,h>0」做保守判定，
宁可漏判也不把配置块当图（war.fls 93 条 `I*` 里只有 **54 条**被判为图像）。

### 3.2 无损验证

| 归档 | `I*` 条目 | 解析→重编码一致 | 疑似图像 |
|---|---|---|---|
| war.fls | 93（I0 73 / I1 20） | **93/93** | 54 |
| skill.fls | 280 | **280/280** | 0（全是信息块） |
| effect.fls | 11 | **11/11** | 2 |

字节级一致只说明「头 14 字节 + body 的切分正确」，**不代表知道像素怎么排**——
这也是下面 §四 的边界。

## 四、为什么还没有「PNG → I0」的像素编码

静态读 `dll` 解码链（`FUN_004586e0` → `FUN_00457f40` → `FUN_00458050`）得到：

1. 头 14 字节后**先**由 `FUN_00457f40` 读 `w*h*8` 字节（每像素 4 个 int16），
   写进 `CImagesRes` 的逐像素结构 `SPixel`（20B/像素，`FUN_00457bf0` 分配 `w*h` 个）；
2. 然后格式解码器读 `u32 count + count*3 调色板 + count 字节运行表 + 像素流`，
   把每个 `SPixel+0x10` 指向流中某段（每像素一段 run），`SPixel+0xc` 是该段长度。

**卡点**：`.res` 头里的 `w*h` 与 `FUN_00457bf0` 收到的宽高不是同一组数。
样本 `war #0` 头写 68×80=5,440，若真按它读 `w*h*8` 需要 43,520 B，但整个 payload 只有
32,353 B。即「宽高到底指什么（单帧？图集？帧数×高？）」未定 —— 在这种状态下写出的
「PNG→I0」只能自洽、游戏读不了，所以**不做假实现**。

要继续推进，最短路径是：读 `FUN_004587b0`（`.res` 完整加载 + `CGetInfo`）确认宽高来源，
再用 `.spr`（`char/<shape>/<state>.spr`）里的帧描述对齐一次。

## 五、散文件回退（路线 C）：函数级证据

### 5.1 结论

| 问题 | 结论 |
|---|---|
| 有磁盘回退分支吗？ | **有**，在 `FUN_00403b50`（图像/精灵类资源加载器） |
| 什么时候生效？ | **只有 `CFile::Open(name, group, "rb")` 失败之后**（=(name,group) 在归档里没命中） |
| 回退路径怎么拼？ | `group + "\\" + name`，**不带 `data\` 前缀**，即相对进程工作目录（`char\9999\stand.spr`） |
| 同步还是异步？ | 异步：`FUN_00440440(path,…)` 建加载任务 → `FUN_00410d90` 入队（向量 push） |
| 能覆盖已有资源吗？ | **不能**：归档命中就不会走到回退 |

### 5.2 代码路径（`客户端源码/dll_export/decompiled_all.c`）

```
FUN_00403b50(name)                                  # 图像加载器，in_EDX = group
  CFile::Open(file, name, group, "rb")              # ① 先按 (名字, 资源组) 打开
  if (文件无效) {
      if (group == 0) → 放弃
      else:
          path = group + "\\" + name                # ② 拼散文件路径（第 2713~2745 行）
          FUN_00440440(path, …)                      # ③ 建任务
          FUN_00410d90(&task)                        # ④ 入队（异步加载）
  }
```

对照：`FUN_00421eb0`（`.igs`/`.occ` 这类 creator）**没有**回退分支——
`CFile::Open` 失败直接返回 0。所以「能不能用散文件」取决于**哪一族加载器**，
不能一概而论（本次只确认了 `FUN_00403b50` 这一族）。

**旁证（文件系统）**：客户端目录里 `map\*.map` 是 14 个 10MB 级散文件，与 `data\map.fls`
（932 条，其中 216 条 `I0` + 30 条 `I1`，余为二进制块）**并存** —— 说明「按资源类型决定
读盘还是读归档」本来就是既有设计，`FUN_00403b50` 的 miss 回退与之并不矛盾。

另有一条**候选**（未坐实）：名字规范化函数 `FUN_00448af0` 在规范化后会检查扩展名，
对 `.SPR/.TXT/.MGC/.PFM/.INI/.DLG` 走特殊分支（`FUN_00999676`，反编译为残桩）。
若成立，意味着这些扩展名可能**总是**读磁盘（优先级高于归档）。这需要动态验证。

### 5.3 怎么验（下一步，需真机）

实验设计（**新增**资源，不碰已有条目）：

1. 选一个服务端能下发、客户端会去加载的**新**造型 id（如 `9999`），
   服务端把 `shape` 改成 9999（`m4_server` 的 `hero_shape`/怪 `shape` 都行）；
2. 在客户端工作目录建 `char\9999\stand.spr`（内容先照抄某个已知可用的 `.spr`，
   需先把 `char.fls` 里对应条目按 f0 反查出来——**条目名哈希尚未移植**，这是前置）；
3. 启动客户端进战斗，看是否渲染出该图 / 是否报资源缺失；
4. 判据：渲染成功 ⇒ 回退可用（且异步）；仍缺失 ⇒ 要么路径不对，要么该族加载器无回退。

**当前阻塞**：字号 ② 需要「名字 → f0」哈希（`StringID`）+ `.spr` 文本格式，
两者都还没移植，所以这一步只能先写成方案，不能假装已完成。

## 六、现有资源替换测试（`res_replace_test.py`）

对 `war.fls` 的**副本**执行，14 项断言全过：

| 用例 | 断言 | 结果 |
|---|---|---|
| A 恒等 | `i0` 解析→编码字节一致；`preserve` 重放与原文件逐字节一致；`compact` 恒等替换后逐条目 payload 一致 | 3/3 |
| B 改头 | 长度不变；除目标条目外其余逐字节不变；只有目标条目变；新锚点生效；宽高未被波及 | 5/5 |
| C 换体 | 长度差正确；compact 尺寸可精确核算；新条目 = A 的头 + B 的体；其余条目内容不变；只读侧 `fls.py` 能正常打开新包 | 5/5 |
| — | `compact` 尺寸公式 + 空隙统计 | 1/1 |

实测数字：目标条目 `#0`（I0 68×80 bpp16 anchor(31,43)，32,353 B），换体用 `#1` 的 body
（13,621 B）；替换后整包 8,384,432 → 8,323,927 B，`fls.py` 读到 181 条、内容正确。

**这一步证明了什么**：容器写回、索引重加密、变长重排、只读侧兼容都成立。
**没证明什么**：客户端**渲染**是否正常（要真机），以及 `.spr` 里的引用是否指向被换的条目。
