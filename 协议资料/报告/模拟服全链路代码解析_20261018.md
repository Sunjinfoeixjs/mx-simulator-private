> 对象：`MX/服务端源码/sim/`（自研模拟服，非官方服务端）  
> 范围：`singleplayer.py` → `m4_server.py` → `tap.py` → `world_config.py` / `drop_data.py` / `magic_cost_data.py`  
> 方法：逐文件通读（宿主 569 行 / ──────────────────────────────────────────────┘  
> │ 进程内直接 new + serve_background()  
> ┌───────────────▼─ 内核层  m4_server.py (3,020) ────────────────────────┐  
> │  M4Server：状态即会话。83 个方法 = 帧构造(44 build\_*) + 业务状态机      │  
> │  run() 单连接 accept → handle() 一个 ~380 行的 if/elif 分派链           │  
> │  \_GMHandler：HTTP 面板，15 个 gm\_* 方法，只绑 127.0.0.1                 │  
> └───────────────┬───────────────────────────────────────────────────────┘

> ┌───────────────▼─ 观测层  tap.py (1,336) + debugger.py (449) ──────────┐  
> │  把 conn 换成 TappedConn → 拿到全部上下行字节，内核零改动              │  
> │  分帧 → 解码(overlay/字典/客户端路由) → 环形缓冲 → SSE 推前端          │  
> └───────────────────────────────────────────────────────────────────────┘  
> ↑ 数据由下两层提供                 ↑ 写入方  
> ┌────────────────────────┬──────────────────────────────────────────────┐  
> │ 配置层 world_config.py │ 真值层 drop_data.py / magic_cost_data.py      │  
> │ (404) 导入期覆盖常量   │ (334 / 2,032) 由客户端数据表生成的只读表      │  
> └────────────────────────┴──────────────────────────────────────────────┘

体量事实：`build_*` 帧构造函数 44 个、`M4Server` 方法 83 个（其中 `gm_*` 15 个）、模块级 `OP_`（S2C）常量 47 个、`C2S_` 常量 50 个、测试 24 个。

**架构上最要紧的一句**：`M4Server` 是**单例状态机**。`_conn / in_war / enemy_hp / enemy_speed / _pending_pet_suffix / _round_defending` 全部是实例字段，没有会话对象。因此「同一时刻只允许一个客户端」不是优化项，而是这套代码的**正确性前提**——`run()` 里那句 `if self._busy: conn.close(); continue` 就是这条前提的守门人。任何并发接入都会静默串台。

## 二、启动链路：端口是动态的，前提是客户端已被配置过

`singleplayer.main()` 的六步，顺序有强因果：

| 步  | 动作                                                      | 关键约束                                                                                                                                                         |
| -- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| ①  | `M4Server(...)` + `serve_background(port)`              | `port=0` → 内核挑空闲端口，`_ready` Event 等 bind/listen 真正完成才返回实际端口                                                                                                  |
| ①½ | `rebuild_server7_bin(port)` + `start_local_http(8080)`  | 客户端 `update.ini` 的 ServerList/MiniPage/DownPage 全指向 8080；不起它会弹「服务器列表需要刷新」+**不可关闭的**「脚本错误」模态框                                                                 |
| ①¾ | `on_ready(srv, port, client_dir)`                       | 调试台挂载点，**必须早于客户端接入**，否则第一条连接抓不到                                                                                                                              |
| ②  | `rewrite_local_ini` + `update_mx_ini` + `check_prereqs` | 见下                                                                                                                                                           |
| ③  | `launch_client`                                         | `mx.exe` 清单是 `requireAdministrator`，Popen 抛 WinError 740 时自动改走 `ShellExecuteEx(runas)`（`_launch_elevated` 包了一个最小 Popen 兼容壳）；**工作目录必须是游戏目录**，否则客户端报「无法获取游戏信息」 |
| ④  | `proc.wait()` → `finally: srv._persist()`               | 客户端退出宿主即退出，不留空转服务端                                                                                                                                           |

第②步是整条链路最脆的一环，三个硬限制：

1. **`local.ini` 必须是明文 GBK**。客户端 `C_sys.RecordString` 是恒等函数，只读明文；写成 `serverini_encode` 的三层加密格式反而不认。
2. **必须已存在指向 `127.0.0.1` 的服务器行**（`f[1]=='127.0.0.1' and f[2].isdigit()`）。`rewrite_local_ini` 只改端口，不改结构；找不到就 `return 2` 中止——**空客户端目录无法一键起服**，必须先手工配置过一次。这是刻意的：宁可中止，也不让客户端误连官方服。
3. **`update.ini` 的 `Version` 必须是 `1.2.73`**，且 `mxmain.dll` 不能是原版 md5 `b50406bc…`（原版加密+压缩仍开启，模拟服只发明文，客户端解不开帧）。

`check_prereqs()` 只产告警不阻断，只有 `--fix-update` 才会真的改文件——这个取舍是对的（不擅自改用户客户端）。

## 三、会话主循环：分派顺序就是契约

`handle()` 的结构是：

```
发 S2C Hello(op1, seed+servernum) 
  → 收 25B 裸明文并校验 (hello_response 的种子混淆 + 22B 零填充)
  → while True: recv_c2s(timeout) 
       战斗指令窗口内 timeout = 剩余秒数，否则 300s
```

分派链 40 余个分支，**顺序本身承载语义**，源码里用注释一条条钉住了：

| 分派                               | 必须排在谁之前 | 理由                                                                                                           |
| -------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------ |
| `C2S_OPENUI(88)`                 | 所有战斗分支  | 战斗中也会点 UI 按钮，落进战斗保底会被错误推成敌方回合                                                                                |
| `C2S_COMMON(192)`                | 所有战斗分支  | 客户端**战斗中也会**批量上报点击统计（sub=1），落进保底会多回一帧 WarTurn                                                                |
| `C2S_PRODUCE(78)`                | 所有战斗分支  | 客户端定时下发（战斗中照发），2026-10-16 实测曾因此多出 WarTurn                                                                    |
| `物品 32-38`                       | 所有战斗分支  | 战斗中用道具走同一批 opcode                                                                                            |
| `C2S_TIME(15)` / `C2GS_TIME(61)` | —       | **两条通道不能混**：op15 回 mxgw 的 10000Hz 滴答，op61 回 dlgcalendar 的 Unix 秒；混用会让时钟漂移校验 `cdt>sdt` 命中 → `Disconnect(007)` |
| `if self.in_war:` 保底             | 最后      | 未识别战斗指令至少回 WarTurn，否则客户端永久停在「请等待」                                                                            |

这个设计的代价：**新增一个 opcode 必须手工判断插在哪个位置**，插错不报错、只表现为帧序错乱。

### 3.1 已做的结构整理（2026-10-18）

分派链从 `handle()` 里搬出来成了 `_dispatch(conn, op, body)`，`handle()` 现在只剩
「握手 → 收包 → 战斗指令窗口记账 → 调 `_dispatch`」。搬运是**纯机械**的：
分支体一字未改，只做了两处等价改写（缩进 -4；3 处 `continue` → `return True`，
语义都是「本帧处理完，收下一帧」）。搬运前后全量回归逐项一致。

更重要的是把「顺序即契约」变成了**数据 + 测试**，而不是注释：

- `m4_server.DISPATCH_PRE_WAR_OPS`：22 条「必须排在战斗保底之前」的 opcode 及其理由。
- `tests/_test_dispatch.py`：在**战斗态**下逐条喂一帧，断言没有回 `WarTurn(114)`；
  同时验证保底本身仍有效（未知战斗指令必须回 WarTurn，否则就是把「不吞帧」做成了「不推进」），
  以及优先区与战斗指令集不重叠。

这样「插错位置」从「只表现为帧序错乱」变成「跑一次测试就红」。代价是新增 opcode 时要同步补一条，
但那条记录本身就是文档。

> 没有做成 `{op: handler}` 字典的原因：40 余个分支里有 12 个带**状态或长度条件**
> （`len(body) >= N`、`self.in_war`、`body[0] == sub`），用字典会丢掉「条件不满足就继续往下试」
> 的语义；要做就得先给每个分支写单测，否则是拿一整条链赌一次改写。当前做法保留了 fall-through，
> 又把最容易出错的部分（相对保底的位置）钉死了。

## 四、进世界：11 类帧，缺一帧就有一处功能坏

`_enter_world()` 的帧序不是随意排的，每一段都对应一个客户端缺陷：

```
PropInit(16)            67 项属性，ITEM_ALL[:-8]
PropResist(18)/Power(19) ★ 末 8 项（5 抗性 + m_At/m_Df/m_Dp）不在 PropInit 里，
                          不发 → CreateProp 留 Default()=0 → 任何 df>0 的招式判 invalid
                          → 提示「无法使用这个招式」
SkillLevel(65) ×2/招式  sktype=2 学进 g_Skills[1]；sktype=7 才装进 g_Skills[6]（战斗菜单）
SceneM(96)              ★ 客户端会 world.ClearAllObject()
AddNpc(99) ×该图全部    ← 所以必须跟在 SceneM 之后逐条补
GotoM(97)
SummonInfo(48)          宠物属性面板
SummonSkill(49)         技能格（hf_from=6 决定护符技能分界）
SetFight(50)            出战标记
SummonKey(53)           birthkey=2 → 头像右下角画「变异」
ItemAdd(33) ×N          逐件推送，没有「整包背包」帧
```

**帧序号即因果**这条规律在本项目里反复出现，最典型的三处：

| 契约                                               | 违反后果                        |

| `S2CItemAdd` 必须在 `WarEnd` + 场景重同步**之后**          | 入包被场景刷新冲掉                   |
| `WarProtect(121)` 必须在 `AttackNormal(117)` **之后** | 客户端在处理攻击命令时才会去后续队列找保护者      |

## 五、战斗：三个字段撑起整个回合状态机

```
await_cmd (bool)          ── 是否在等玩家/宠物指令
cmd_deadline (float)      ── 到点则默认普攻（对齐 warui.ShowTimer(30)）
_pending_pet_suffix(list) ── 主角已结算、宠物指令未到，剩下的慢位单位挂起等它
```

一个回合的完整生命周期：

```
_start_war:  回满血 + 回满资源 → WarStart(112) → WarAdd(115)×(主角,[宠物],敌方N)
             → WarTurn(114) → _arm_cmd_timer()
         ↓
handle 收到 160/161/163/165/167（或超时）
         ↓
_resolve_hero_round(hero_act):
    order = 按速度降序（HERO 100 / PET 49 / 敌按造型查表，同种 -5 递减）
    prefix  = order[:index(HERO)]       ← 比主角快的敌人，先动
    hero_act()                          ← 主角的 act 闭包
    suffix  = order[index(HERO)+1:]
      before_pet = suffix[:index(PET)]  ← 先 WarTurn(1) 再结算
      ★ 遇到 PET → _pending_pet_suffix = after_pet; _arm_cmd_timer(); return
      after_pet  结算 → WarTurn(0) → _arm_cmd_timer() → _round_done()
         ↓
handle 收到 168-174 → _finish_pet_turn(): 执行宠物指令 → 结算 after_pet → WarTurn(0)
```

五个入口（普攻 / 招式 / 防御 / 道具 / 其它战斗指令）全部收敛到 `_resolve_hero_round`，只有宠物指令走 `_finish_pet_turn`——这是有意的，因为客户端的交互顺序是「先交主角指令 → 再开宠物菜单 → 交宠物指令」。

**几个值得记住的取值**（都有录像或源码依据，不是拍的）：

- `HERO_WAR_ID = 100`，**必须非 0**。客户端 `war.Add` 用 `war.g_HeroID = obj.m_ID` 命中主角，而全代码到处 `if war.g_HeroID and ...`；id=0 会让整条「玩家可操作」链路失效（点敌人什么都不发），表现为「指令菜单不出现」。
- `WARD_HIT=1` 才是「造成伤害」。`ward=0` 会落进 `BeginHit()` 的 `Evade()` 分支，演成闪避且不播打击特效。
- `hp_chg` **正数=扣血**。三条独立依据（testwar.py 样例、card_game.py、`CreateModifyHP` 的 `hp>=0` 分支）。
- `life=2` 才会 `obj.Die()`；`life=3` 是删除。
- `ENEMY_SPEED_BY_SHAPE = {1: 115, 2130: 40}`、`ENEMY_SKILLS_BY_SHAPE = {1: [1103], 2130: [415]}`、`ENEMY_HURT_BS_BY_SHAPE = {1: 0.0, 2130: 1.0}` —— 三张表都是 137 场录像校核出来的，且都被 `world_config` 覆盖。

**伤害目前是常量而非公式**：主角 50 / 宠物 48 / 敌方 20，敌方 HP 100、主角 400、宠物 350。没有攻防命中抗性的计算过程。这不是偷懒——`.mwr` 录像只给结果不给公式，客户端 `m_NextExp` 也是服务端下发，本地无 `expdata` 表可反推。所以「数值管线」这块是**结构性缺口**，不是待办。

## 六、帧编码：MSB-first 是全局陷阱

```python
make_s2c:  [1B N][opcode][data]      N 含 opcode；N>=0xFF → 0xFF + u16
recv_c2s:  [opcode][1B N][body]      N 不含 opcode
var_gbk:   GBK 字节 + \0（C 字符串，无长度前缀）
```

两处最容易写错的位域，都由 `mxmain.dll` 的 `UnpackBit`（VA `0x41a4d0`）定死：**off=0 对应 bit7（MSB-first）**。

| 帧                         | 客户端读法                                                         | 实际字节布局                                                               |           |        |
| ------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------- | --------- | ------ |
| `WarAdd(115)` bitfield    | `allied=UnpackBit(0,1)`                                       | `allied` 在 **bit7(0x80)**，type=bit6，child=bit5                       |           |        |
| `WarWState(123)` bitfield | `hurt=UnpackBit(0,4) life=UnpackBit(4,2) ward=UnpackBit(6,2)` | `hurt` 在 **bit7..4**、`life` 在 bit3..2、`ward` 在 bit1..0 → \`(hurt<<4) | (life<<2) | ward\` |

`allied` 按 LSB 发（0x01）会让所有单位都算敌方——这是历史上「玩家在对面」的根因。这条教训值得贴在墙上：**这个协议的位域，off 从小到大对应从高到低**。

另有两个非帧特例：

- 握手后客户端回的是**25 字节裸明文**（3B 种子混淆 + 22B 零填充），不是帧。`tap.feed()` 里有专门的 `_raw_c2s=25` 裸区处理，否则首字节会被当长度、缓冲永久卡死。
- `op 250` 是客户端 `C2GS_PING` 的死常量（定义了从不使用），服务端拿它当 PING 回显够用，但**别指望客户端有反应**。

## 七、数据层：配置在导入期就固化了

`world_config.apply_to()` 在 `m4_server` **模块导入期**执行（`sys.modules[__name__]`），位置被刻意放在「所有可被覆盖的常量之后、任何运行逻辑之前」。推论：

- 编辑器 `editor_server.py` 改完 `world_config.json` **必须重启内核**才生效，没有热重载。
- 校验不过 → 整体跳过，永不部分应用（保证一致性）；`--no-world-config` 是回归测试的确定性逃生舱。
- `MAPS/MAP_EXITS/MAP_LINKS/NAME2MAP` 用 `clear()` + 回填原地 mutate，避免外部引用失效——这个细节做对了。


`drop_data.py` 是**真值表**：43 个场景，来自《资料全库》场景表 × `itemdata.py` 的真实 item id。但**概率和件数是模拟参数**：`DROP_CHANCE=0.6`、`DROP_MAX_PER_BATTLE=1`。资料表只写「哪个场景掉什么」，没给概率。城镇（永泽城/谷雨镇/清溪城）不在表里 → `scene_pool()` 返回 None → 不掉落，与「只有野外才有掉落」的口径一致。

`magic_cost_data.py`（2,032 行）同理：`MAGIC_COST` 由 `magicdata.py` 的 mana/fp/at/df/dp 表达式在 `slv=1` 求值生成，`MAGIC_INFO` 来自资料全库招式表。

## 八、观测层：零侵入是怎么做到的

`tap.py` 的设计前提是「内核有 95 处裸 `conn.sendall`，逐点插桩必漏」。解法是把 `conn` 换成 `TappedConn`（鸭子类型 + `__getattr__` 透传），只替换 `M4Server.handle` 和 `M4Server.log` 两个方法：

```
sendall(data) → 丢弃过滤 → tap.feed('S2C', data) → 底层 sendall
recv(n)       → 0.1s 分片读 → 片间检查注入队列 → 攒够 n 才返回
```

`recv` 必须分片的原因写得很清楚：裸 `socket.recv` 一阻塞就无法从外部唤醒，注入的伪造帧要等客户端下次说话才生效，调试时表现为「点了注入，内核没反应」。而分片超时**不能外泄**（否则 `recv_exact` 正在攒的半帧会被丢，直接串帧），只在本层重试。

分帧器 `Reassembler` 带失步自愈：积压超 4096B 仍切不出帧，就逐字节前移重新对齐，跳过的字节数上报到界面——**不隐藏偏差**是这层的设计原则（`decode_best` 的 `tail`/`note` 同理）。

解码三层优先级：`OVERLAY`（手写精确布局，对齐 `build_*`）> C2S 字典字段表（同 opcode 多形态逐种试配）> S2C 用 `net.py` 的 `NET_FUNCTION_NAME` 桥接字典。覆盖率的分母取**客户端上行常量全集**（`C2S_*` + `C2GS_*`），不是字典——因为字典会漏项，分母少了直接让待实现清单漏工作。

## 九、读码发现：两处解码层与内核实际帧不符（**已修复**）

这是通读时比对出来的，**不影响游戏运行**，但会误导「用调试台看真值」这个工作流。

> 2026-10-18 修复完成。改动只在解码层与界面展示，内核一行未动；`tests/_test_tap.py` 同步更新了按旧位序写死的断言，并补了 op17 的宽度用例。两处修复后的实测输出见各节末尾。

### 9.1 `WarWState(123)` 位域方向相反（较严重）

- 内核发送（`m4_server.py:1067`）：`bitfield = ((hurt & 0xF) << 4) | ((life & 0x3) << 2) | (ward & 0x3)` → hurt 在高 4 位。
- 调试台解析（`tap.py:1066`）：`hurt, life, ward = bf & 0xF, (bf >> 4) & 0x3, (bf >> 6) & 0x3` → hurt 在低 4 位。
- 同一文件的 `_OV_NOTE[123]` 注释也写成 `bit0-3=hurt，bit4-5=life，bit6-7=ward`，与内核注释（`bit7..4=hurt`）矛盾。

实证（本次实跑 `build_war_wstate` → `FrameTap.feed`）：

```
内核发送 hurt=1 life=0 ward=1 hp_chg=20
线上字节: 07 7b 01 11 14 00 00 00   → bitfield=0x11
调试台拆解: hurt=1 life=1 ward=0
战斗模型日志: 单位1 hp_chg=20(扣 20) · hurt=1 life=1 ward=0
```

`life=1` 是「不省人事」——不会误判死亡（判定走 `life==2`），但战斗日志里「hurt/life/ward」三项全错位，用它核对「敌方伤害是否真的 ward=1」会得到相反结论。

**修复**：`tap.py` 拆位改为 MSB-first，同时把拆好的三项存进世界模型，界面只显示、不再二次拆解（第二处拆解本来也是错的，正是它让「改一处忘另一处」变成必然）：

```python
hurt, life, ward = (bf >> 4) & 0xF, (bf >> 2) & 0x3, bf & 0x3
u['last_hurt'], u['last_life'], u['last_ward'] = hurt, life, ward
```

`_OV_NOTE[123]`、`debugger.html` 的说明文字、`协议资料/规格/M4_协议规格.md`（§3 表格 + §3.1）四处同步对齐，并在规格里补了 `0x11` 的换算例子——错误位序在这批文档里存在了至少两版，根因是「`UnpackBit(0)` 的 0 是最高位」这句没有一个地方写明。

修复后实测：`0x11` → `hurt=1 life=0 ward=1`，战斗日志同文。

### 9.2 `PropChange(17)` 的 value 宽度被写死 4B

`_OV_S2C[17] = ('S2CPropChange', 'type:1 value:4')`，但内核按 `ITEM_ALL[type]` 的字宽发送：`m_HP`=2B、`m_At/m_Df/m_Dp`=1B、`m_Gold/m_Exp`=4B。

后果（实测）：`build_prop_change_hp(400)` 的 3B body 解出来是

```
[('type', 16, '16'), ('value', None, '← 越界（需 4B 剩 2B）')]
```

**数值直接丢了**，只剩 `type=16` 和 hex。`fit` 仍为 `True`（越界时游标被置到末尾，`consumed==total`），所以界面不会打黄色「布局不符」，坏的是一条更隐蔽的路径：**主角血量/资源在调试台里永远是 None**。而每场战斗开场就发 6 帧（1 帧 HP + 5 帧资源），战斗一开打这批帧全部无法读数。

**修复**：不做「几个特例」，直接按客户端 `src/hero.py:ITEM_ALL` 建全表——75 项（下标 0..74），每项带属性名与字宽，导入时 `assert len == 75` 兜住「少一项就整体错位」这种静默灾难：

- `tap.py:_ITEM_ALL_SPEC` —— 下标即顺序，token 如 `m_HP:2` / `m_Cash:8` / `m_Name:f20` / `m_Resist_Xian:1s`。
- `tap.py:_dyn_prop_change(payload)` —— 读首字节 type，产出 `type:1 <属性名>:<宽度>`；`describe()` 新增可选 `payload` 参数，只有登记在 `_OV_DYN` 里的编码才走动态路径，其余编码行为不变。
- 宽度不可静态确定时（未知下标 / `m_Desc` 这类变长结构）**不猜**：退化成 `type:1 value:T`（吃掉剩余字节）并在 note 里说明，既不越界也不假装知道宽度。

字段名也从 `value` 变成属性名，`m_HP=400` 一眼可读。修复后实测：

```
type=16 m_HP   → 400     fit=True
type=72 m_At   → 100     fit=True
type=43 m_Gold → 50000   fit=True
type=200       → 2B tail（「超出 ITEM_ALL 范围 0..74」）
type=2 m_Desc  → 2B tail（「变长结构 TDESC」）
```

顺带发现一处内核的同类隐患（未改）：`build_prop_change(idx, value, width=8)` 会**静默落进 2B 分支**（只认 1/4，其余按 2），当前无调用方传 8，故属潜伏项而非现网 bug。

### 9.3 一处潜在路径（当前不可达）

`_resolve_hero_round` 里，如果宠物速度排在主角之前（`PET_SPEED > HERO_SPEED`），`prefix` 含 `PET_WAR_ID`，`_unit_act` 会**无条件 `_pet_attack`**——忽略玩家提交的宠物指令。当前 `PET_SPEED=49 < HERO_SPEED=100`，宠物恒在 `suffix`，所以是死路径；但 `world_config` 没有 `pet_speed` 键，若将来把宠物速度调高，行为会静默变成「宠物只普攻」。

## 十、结论

**这套代码的真实工程质量高于「模拟服」这个称谓**：帧格式、位域、符号、帧序这四类约定全部有客户端源码 / 反汇编 / 录像的三重依据，且都写进了注释；不确定的地方（掉落概率、经验曲线、伤害公式）明确标成模拟参数而不是伪装成真值。持久化那一段也值得单提：原子替换 + `_save_blocked`（存档读不出来就禁用自动保存，绝不覆盖）+ 加载时拒绝非 dict 根节点与非法 ID。

**三个结构性缺口**（不是 bug，是数据不可得）：

1. **战斗数值无公式**，只有常量。客户端本地没有规则表，真值只能靠更多 `.mwr` 录像拟合。
2. **经验/金钱曲线是手写常量**。原计划「按 expdata 反推」的前提已被证伪（全库无该表、`m_NextExp` 由服务端下发）。
3. **上行 opcode 覆盖不全**。客户端能发约 136 条，内核显式处理 50 条左右，其余落进 `（未识别 op=N）` 或战斗保底。调试台的 `c2s_nodef` / `undict_c2s` 就是这份清单的实时视图。

**两处解码偏差已修**（见第九节）：WState 位域改回 MSB-first，并把拆解结果沉淀到世界模型、界面不再二次拆；`PropChange` 改为按客户端 `ITEM_ALL` 全表（75 项）动态选宽，宽度不可定时降级为 tail 而非猜。都只动 `tap.py` + 界面，内核未动。

**回归现状**：`tests/_test_tap.py` 除两条**与被改代码无关的陈旧断言**外全绿——  
① 「NPC 对话 + 商店 147」：测试第 3 次移动（`encounter_every=3`）必然进战斗，紧接着点 NPC，而 147 只在选到购买选项时才发，不是点击即发；  
② 「一回合内 WarWState ≥2」：服务端此时停在「等宠物指令」，第二个 wstate 要等宠物超时后敌方行动，2.4s 内收不到。两条都只依赖帧数/C2S 分支，与解码改动无交集。修它们要改测试意图，留着待定。
