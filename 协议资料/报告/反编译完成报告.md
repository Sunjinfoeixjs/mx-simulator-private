## 二、过程中发现并修正了自己的一个错误

反编译产物一出来就暴露了问题：

```
   39  BINARY_ADD
   40  LOAD_CONST  0   ; None
   43  POP_TOP
```

`BINARY_ADD` 出现在语句末尾 —— 不合常理。于是对全量产物做了**上下文统计**：

### 证据 D：前驱/后继画像

```
0x41（我当时标为 BINARY_ADD）的前驱:
   CALL_FUNCTION   43.25%   <- 调用后丢弃返回值 = POP_TOP 场景
   JUMP_IF_FALSE   26.06%   <- 分支汇合点
   JUMP_FORWARD    19.79%   <- 分支汇合点
   JUMP_ABSOLUTE    4.81%   <- 循环/汇合
   ---------------------------------
   跳转落点合计    50.66%   <- 一半实例是跳转落点!

0x41 的后继:
   LOAD_FAST       38.36%   <- 语句起点
   LOAD_CONST      23.59%
   LOAD_GLOBAL     14.35%
```

后继分布就是「新语句起点」的画像。**`BINARY_ADD` 不可能有 50% 的实例是跳转落点**——
那会栈下溢（二元加法需要 2 个操作数，而 `CALL_FUNCTION` 后栈上只有 1 个结果）。

结论：**`0x41 = POP_TOP`**。旧档是对的，我此前把它"修正"成 `BINARY_ADD` 是错的，已回退。

### 证据 E：代码对象内位置分布（最强判据）

统计每个 opcode 出现在「代码对象最后一条指令」的比例：

| opcode | 出现次数 | 位于函数末条 | 占比 |
| --- | --- | --- | --- |
| **0x55** | 4,331 | **3,437** | **79.36%** |
| 0x41 | 15,973 | 2 | 0.01% |
| 0xc1 | 29,502 | 0 | 0.00% |
| 0x8f | 22,409 | 0 | 0.00% |

只有 `RETURN_VALUE` 才有「绝大多数出现在函数末尾」的特征（函数每个出口都要返回）。
**`0x55 = RETURN_VALUE`** —— 这也纠正了我此前把 0x55 当 `POP_TOP` 的判断。

> 这个判据是我在这次工作中新引入的，比频率画像和结构指纹都更硬：
> 它是**编译器行为的直接统计**，不依赖我对反编译体的人眼解读。
