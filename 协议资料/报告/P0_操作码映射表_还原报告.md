**核心修正**：早期报告（`README.md` 与 `解密运行报告.md`）判定为「操作码被**置换**（permutation）」——
该结论**不准确**。真实机制是**操作码重编号（renumbering）**：

- 客户端把 CPython 2.6 的每个 opcode 重新指派为一个**任意 1 字节值**，映射本身**不保持任何结构关系**（既非置换的排序，也非等距平移）；
- **但保留了 CPython 的「是否带参数」判定语义**，只是**阈值从标准的 `>= 90 (0x5A)` 改为 `> 0x5E (94)`**。

第二条（阈值改变 + 阈值恰好卡在 0x5E）是本次能完整解出映射的**关键突破口**——
它让「带参数/不带参数」的划分重新变得可判定，从而把问题从「指数级搜索」降为「逐条对证据求解」。

## 二、解码规则（客户端字节码格式）

```python
THRESHOLD = 0x5E          # 客户端阈值：op > 0x5E 才读 2 字节参数

def decode(code):
    """解码为 [(offset, obs_op, arg)]；arg=None 表示无参数。"""
    out, i, n = [], 0, len(code)
    while i < n:
        op = code[i]
        if op > THRESHOLD:
            if i + 2 >= n:
                raise ValueError('指令截断 @ %d' % i)
            out.append((i, op, code[i+1] | (code[i+2] << 8)))   # 小端 16 位
            i += 3
        else:
            out.append((i, op, None))
            i += 1
    return out
```

Ghidra 反编译中对应的原始分派代码（`decompiled_all.c`）：

```c
uVar15 = (uint)(byte)*local_4c;          // 取当前操作码
uVar17 = 0;
puVar3 = (ushort *)((int)local_4c + 1);
if (0x5e < uVar15) {                     // ★ 阈值 0x5E，非标准 0x5A
    uVar17 = (uint)*(ushort *)((int)local_4c + 1);   // 读取 2 字节参数
    puVar3 = (ushort *)((int)local_4c + 3);          // 推进 3 字节
}
```

## 四、客户端的「融合超级指令」设计（重要发现）

客户端在 peephole 阶段做了**指令融合**，这解释了一批「多对一」观测值：

1. **`FOR_ITER` + `GET_ITER` 融合**
   `case 0x36` 的循环体在迭代器为空时会**直接融入** `GET_ITER` 的处理路径
   （`switchD_0048d3a3_caseD_71` / `_caseD_6c`）。
   因此 `0x36`（= FOR_ITER）与 `0xAF`（= GET_ITER）在语料中几乎成对出现：
   实测 `0xAF` 4,983 次、`0x36` 4,981 次，差值 2 —— 符合融合设计的预期。

2. **调用族 argcount 改走操作数栈**
   `0x28`–`0x2B` / `0x48`–`0x4B` / `0xDA`–`0xDD` 这些**不带字节参数**的调用指令，
   其参数个数从**操作数栈**读取（而非 opcode 后的字节）。
   这直接导致 `CALL_FUNCTION` 的 `oparg` 统计（平均 5.345）**不表示真实参数个数** —— 属正常现象。

3. **`0xBC`（= DUP_TOP）为融合路径产物**，与 `0x30`（= DUP_TOP）同义。

## 九、归档同步中发现并修复的一个前置缺陷

本次把工具链同步进归档时，发现 `pymarshal26.py` 存在一个**会静默破坏结果的严重缺陷**：

- `co_code` / `co_lnotab` 是**纯二进制字节串**，但解析器一律走 `self.object()` → `str.decode('gbk','replace')` 路径，
  把操作码字节按 GBK 文本解码，**非法字节被替换为 U+FFFD**（如 `0x8F` → `\ufffd`）。
- 后果：`opmap.get_code_bytes()` 再从字符串反编码回字节时抛 `UnicodeEncodeError`；
  即便强行绕过，操作码也已**不可逆丢失**，映射验证将完全失真。

**修复**（已应用于工作版与归档版，两者 `pymarshal26.py` 现字节一致，MD5 `7f48679aa0b76e5c3ae07c77757e3b46`）：

```python
# MarshalReader.__init__
self.raw_mode = False        # co_code / co_lnotab 是纯二进制，绝不能按文本编解码

# 读取 code object 时
self.raw_mode = True
co.code = self.object()      # 原样保留 bytes
self.raw_mode = False
...
self.raw_mode = True
co.lnotab = self.object()    # 同理
self.raw_mode = False

# 读字符串分支
if code in (TYPE_STRING, TYPE_INTERNED):
    n = self.long(); raw = self.take(n)
    if self.raw_mode:
        return bytes(raw)    # ★ 二进制模式：不做文本解码
    ...
```

> 该缺陷只影响「反汇编/映射验证」路径，**不影响**先前报告中「常量、变量名、中文字符串可完整读取」的结构性结论
> （那些字段确实是文本，理应走 GBK 解码）。修复后已完成端到端复验（见下）。
