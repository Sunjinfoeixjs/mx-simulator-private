运行提示
--------
· 模拟服默认监听 127.0.0.1:3134；依赖同目录的 magic_cost_data.py（已随 sim/ 一并复制）。
· 脚本按 __file__ 上溯三级定位项目根：在 sim/ 内运行 m4_server.py 时，根 = MX/，
  会自动在 MX/ 下创建 logs/ 与 data/save/（role.json）。若希望沿用 Claw 的存档与日志，
  请改在 Claw/tools/sim 下运行原脚本。
· role.json 先写入同目录临时文件，再以原子替换提交；写入或替换失败时旧存档保留，
  避免进程中断留下半截 JSON 覆盖已有进度；非对象根节点的 JSON 存档会被拒绝加载，
  hero_res/items/tasks 非对象容器与无效 ID 也会被拒绝。序列化错误会作为存档失败返回
  而不覆盖旧档。若启动时发现现存存档不可读取，本次
  运行会禁用自动保存并告警，避免默认新状态覆盖无法解析的旧进度；先手动备份并修复
  或移走该存档后再重启，才能恢复保存。
· `_test_role_persistence.py` 覆盖原子替换、失败保留、无效 JSON 与损坏存档保护。
· tests/ 下有一批「接线型」测试（_test_gm / _test_item / _test_pet / _test_war2 /
  _test_battle_speed / _test_explore / _test_time_minerals / _test_openui_group）
  **不自起服务器**，直接连固定端口（3135-3144）。跑之前须先
  `python m4_server.py --port <该测试的 PORT>`，否则报 ConnectionRefused。


调试台（2026-10-17 新增）
------------------------
动机：《项目完成度评估》把「C2S 覆盖 30.7% / S2C 21.6%」列为头号待办，而在这之前
**没有任何一处在看真实字节流**——m4_server 只有 self.log 的文字描述，未识别的指令
只留一行「（未识别 op=N）」，既不知道对方发了什么，也不知道自己回了什么结构。

    python debugger.py                 # 内核 + 客户端 + 调试台（一条命令）
    python debugger.py --no-client     # 只起内核 + 调试台（脚本联调）
    start_debugger.bat                 # 同上，双击即可
    → 浏览器打开 http://127.0.0.1:8090/

五个页签
  帧流      实时上下行帧列表（opcode / 名称 / 摘要），点开看逐字段解码 + hex。
            字典无编码、服务端未实现、布局不符的帧分别标红/橙/黄 —— 这就是待办清单。
  地图      SceneM / AddNpc / MapTrack / GotoM 实时翻译成地图：玩家、NPC、出口、轨迹。
  战斗      War* 那十来种帧翻成「谁在场 / 谁打谁 / 谁掉多少血 / 谁死了」：双方单位卡
            （阵营、血条、累计扣血、受击次数、死亡态）+ 语义化动作时间线，点任一条可
            跳回帧流定位到那一帧。WarWState 的位域原样摊开（hurt/life/ward），
            hp_chg 既显示原始值也标注本服符号约定 —— 免得把「正数=扣血」看反。
  协议覆盖  本会话出现过的编码 vs 全表（已实现 / 未实现 / 未出现 / 字典未登记）。
  状态·GM   实时状态 + GM 热操作 + 帧注入 + 丢帧（进程内直调，不经 HTTP 中转）。

  心跳：平时 state/stats 每 2s 一推，进战斗自动提到 0.3s（回合制一步一变，2s 会明显滞后）。
        帧流本身是 0.12s 批推，与心跳解耦。

怎么做到「不改 m4_server」：内核拿到的 conn 只是 sendall/recv/settimeout/close 四件套，
tap.install() 只替换 M4Server.handle 与 log 两个方法，把 conn 换成 TappedConn 就拿到
全部字节（95 处裸 sendall 一处不碰）；C2S 侧的 25B 握手明文单独识别为「裸区」，
不喂进分帧器。

解码三层来源：① 本文件内 OVERLAY 精确布局（41 个 S2C 帧，逐字段对齐 build_*）
② 协议资料/字典/protocol_functions.json 的 C2S 字段表（同 opcode 多形态逐种试配）
③ 客户端 客户端源码/src/net.py 的 NET_FUNCTION_NAME 把 S2C opcode 桥接到字段表。
布局对不上时**不隐藏**：多出的字节进 tail、越界写进 note，而不是给个漂亮但错的解析。

覆盖率的分母（2026-10-17 校正）
------------------------------
之前三个数字各说各话，谁都不等于谁：

    协议资料/字典/protocol_c2s_full.txt   121 条（人工清单）
    字典 protocol_functions.json          131 条（调试台原分母）
    《项目完成度评估_20261016》手写        137 条
    客户端源码/src/net.py 的常量          **136 条** ← 只有这个是权威
                                          （C2S_* 121 + C2GS_* 17，去重后 136）

查下来两处偏差都真实存在：
· 人工全表清单**漏掉整个 C2GS_* 族**（6 21 57 58 59 61 65 90 91 93 94 135 155 250…）。
  这批同样是客户端发出去的上行编码，漏了就永远不会出现在待办里。
· 字典有 4 个条目（28 60 95 136）在客户端找不到对应常量，疑似幻影——照着做是白做。

**分母少一个，待实现清单就漏一项，使用者就漏做一份工作**，所以现在取客户端常量为分母，
字典降级为「字段定义来源」，并把两侧差异显式列出：

  · 「字典缺字段定义」9 个：8 15 90 91 114 125 135 158 250
    —— 客户端会发、但字典解不出字段，出现时只能看 hex
  · 「疑似幻影」4 个：28 60 95 136

协议覆盖页有「字典缺定义」过滤器可直接筛出前者；每行的来源标签（客+典 / 客 / 典 / 精 / 无）
标明该编码两个来源的命中情况，悬停有说明。

**两个维度要分清，别混成一句「未实现」**：
  · 「服务端未实现」= 内核日志旁听来的（`（未识别 op=N）`），是运行时证据；
  · 「字典缺字段定义」= 客户端会发但字典没条目，是**逆向覆盖**的缺口。
两者互相独立：op 8（C2S_PING）服务端早就实现了，字典里却查不到 → 它属于后者不属于前者。

**再澄清一条容易误判的**：「客户端无路由的 S2C」**不是故障**。客户端 net.py 的
`OnServerCmd` 遇到没注册的 opcode 会打印 `OnServerCmd: 0xNN` 与
`!!!! func==None, OnServerCmd: 0xNN` 两行，然后 `return` ——不崩、不弹框，只是这一帧
没人处理。所以它的准确含义是「服务端在自嗨：看着像有应答，客户端其实什么也没做」。

  实例：**op 250**。客户端 `C2GS_PING = 250` 是个**定义了却从不引用**的死常量
  （整个客户端源码里只有它那一行），服务端却拿 250 当 PING 回显的 opcode。
  拿它当链路探针够用（能验证内核读到了帧），但别指望客户端有任何反应。

交互巡检 coverage_smoke.py
-------------------------
    python coverage_smoke.py            # 几秒钟，产出覆盖清单
    python coverage_smoke.py --md r.md  # 同时落一份 markdown
    python coverage_smoke.py -v         # 看每一步的收发

调试台是「看实时流量」，巡检是「一次性把全景摸清」。它脚本化走一遍全部已知交互
（登录→进世界→移动→NPC 三级菜单→商店→任务→宠物→物品→UI→帮派→18 种战斗指令），
然后把剩下没踩到的编码逐个发一遍——这些只会命中内核的「未识别 op=N」兜底，
副作用就是一条日志。于是「服务端到底做了多少」变成了运行时硬证据，不再靠手数。

★ 一条不能省的规矩：**已实现的编码绝不能用通用探测 body 发**。长度不符会被内核的
  长度检查挡下、落进未识别兜底，把「已实现」误报成缺口——那比漏报更糟，会让人去做
  已经做完的事。所以脚本里维护一份 `KNOWN_HANDLED`（从 m4_server 分支人工抄出，
  含 `range(168,175)` 与两处集合运算展开的结果），探测段一律跳过它们，只让它们走
  真实路径；报告里再用它做交叉校验，把误报直接标出来。

首次巡检结果（2026-10-17）：
    上行分母 136 · 本次踩到 136 = 100%（全量探测）· **未实现 86 · 已实现 50**
    136 − 86 = 50，与人工核对的清单**完全一致**，交叉校验 0 误报
    下行分母 168 · 本次出现 42 = 25.0%
    待办按模块分组，最大的三块：nethero 15 个、netnpc 13 个、netplayer 7 个
    （所以《项目完成度评估》说的「42/137 = 30.7%」量级没错，只是分母和清单都不准）

**历史快照**，不要再当现状看；现状请直接问调试台。
