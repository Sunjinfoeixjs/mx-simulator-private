# 单机游戏架构（2026-10-16）

> 把「客户端 + 模拟服」两个进程、两套生命周期，改造成**一个进程管全部**的单机游戏形态。
> 本文记录改造动机、目标架构、文件级改动、取舍与验证结果。

---

## 一、改造前的形态与问题

```
mx.exe（官方客户端，CPython2.6 + 明文补丁 DLL）
   │  TCP 127.0.0.1:3134（端口硬编码在 prepare_local_client.py / local.ini / server7_local.bin 三处）
   ▼
m4_server.py（独立进程：阻塞 accept 循环 → handle(conn) if/elif 分发链）
   ├─ save/role.json
   └─ GM 面板 0.0.0.0:8080（可选）
另有：local_http.py 8080（HTTP 劫持，需第三个进程/窗口）
```

四个具体痛点：

| # | 问题 | 后果 |
|---|---|---|
| 1 | 端口 3134 硬编码在三处 | 端口被占用 → 客户端「连接服务器失败」，且改一处漏两处 |
| 2 | 三套生命周期 | 先起哪个后起哪个有耦合；客户端崩了服务端空转；反过来服务端没起客户端连不上 |
| 3 | 单连接假设是隐式的 | `M4Server` 状态全挂实例属性（`_conn`/`in_war`/`enemy_hp`），第二个客户端连上来会静默覆盖状态 |
| 4 | GM 面板绑 `0.0.0.0` | 调试面暴露到局域网 |

## 二、目标架构

```
┌─ singleplayer.py（唯一进程，一条命令 / 一个 bat）──────────────────────┐
│                                                                      │
│  GameKernel   m4_server.M4Server（守护线程）                          │
│                · 登录/选角/进世界/移动/NPC/回合制战斗/物品/宠物          │
│                · 单机路径：状态即会话（单角色单连接，显式拒绝并发连接）    │
│                · 多会话：MultiServer 每连接一个 M4Server，互不干扰       │
│                · 存档 role.json（--save-dir 可注入）；多角色时按账号     │
│                  分文件 role_<账号>.json，老 role.json 由首个账号认领    │
│  Transport    LoopbackListener 127.0.0.1:0 → 自动空闲端口              │
│  HttpHijack   127.0.0.1:8080（客户端 update.ini 的 ServerList /        │
│                MiniPage / DownPage / GuidePage 全指向这里）             │
│  ClientCfg    local.ini（明文 GBK，端口跟随实际监听端口）               │
│                + mx.ini（serverini= / refreshserver=，只动这两个键）     │
│                + 前置校验（update.ini 版本 / mxmain.dll 补丁状态）       │
│  ClientHost   mx.exe 子进程托管；宿主管理客户端生命周期                 │
└──────────────────────────────────────────────────────────────────────┘
```

这里的“合并启动”指由同一个宿主入口启动内核、配置客户端并托管客户端退出；
游戏内核运行在宿主的守护线程中，`mx.exe` 仍是独立子进程，通过本地 TCP 回环通信。
客户端二进制不与 Python 宿主合并到同一个操作系统进程。

四条设计约束：

1. **不引入新协议**。帧格式仍由 `m4_server.make_s2c` / `recv_c2s` 定义，传输层只搬字节，
   不解析、不改写、不加解密。
2. **不假装解决加密**。明文通道依赖 `mxmain_nocrypto.dll`（`+0x72` 一字节补丁）。
   `transport.py` 刻意**不**接入 `protocol_crypto.ReferenceStreamCipher`——占位加密比
   没有加密更危险（会让人误以为链路是安全的）。
3. **不改客户端**。客户端侧（484 个脚本 / 44 个 `net*.py` / `C_net` 原生栈）零改动，
   仍走真实 TCP 回环；`0x43cc50`  VMProtect 缺口原样保留，绕开而非解决。
4. **旧用法不破**。`python m4_server.py`（独立进程 + 固定端口）、`_e2e_*.py`、
   10 个 `tests/_test_*.py` 保持原样；`start_local_test.bat` 保留为兼容入口，
   转发到统一的 `start_singleplayer.bat`。

## 三、文件级改动

### 新增

| 文件 | 作用 |
|---|---|
| `sim/singleplayer.py` | 单机宿主：内核线程 + HTTP 劫持 + 客户端配置 + 客户端托管 + 生命周期 |
| `sim/transport.py` | 传输抽象：`LoopbackListener`（回环监听，`port=0` 自动选端口）、`make_memory_pair()`（进程内双向管道，零 socket 自测用）、`RejectingConn` |
| `sim/start_singleplayer.bat` | 一键启动（自动定位 Python，参数透传） |
| `tests/_test_singleplayer.py` | 单机架构回归测试（20 组断言，全离线） |

### 修改 `sim/m4_server.py`（外科手术式，6 处）

| 处 | 改动 | 兼容性 |
|---|---|---|
| `load_role(path=None)` / `save_role(data, path=None)` | 存档路径可注入 | 默认仍走模块 `SAVE_PATH`，行为逐字节不变 |
| `M4Server.__init__(..., savedir=None)` | 新增 `self.savepath` / `self._ready` / `self._busy` | 原位置参数签名不变，既有 10 个测试与 `_e2e_*` 不受影响 |
| `serve_background(port=0, web, web_port)` | 新入口：守护线程起 accept 循环，返回真实端口 | 纯新增 |
| `run()` | ① `port=0` 回填 `getsockname()`；② `_busy` 单连接保护；③ `_ready.set()` | 独立进程跑法不变；多连接从「静默覆盖」变为「显式拒绝」 |
| `_start_web()` | `0.0.0.0` → `127.0.0.1` | 调试面不再暴露局域网 |
| `main()` | 新增 `--save-dir` / `--single`（转交宿主） | 原 CLI 参数与行为不变 |

> `handle(conn)` 及全部 ~80 处 `conn.sendall(...)` **一行未改**——`conn` 始终是鸭子类型
> （`sendall`/`recv`/`settimeout`/`close`），所以同一个内核既能跑真实 socket，
> 也能跑 `InMemoryConn`。

## 四、关键取舍

**为什么保留真实 TCP 回环，不做「进程内直连」？**
客户端是官方 `mx.exe` 原生二进制，网络栈在 `mxmain.dll` 的 `C_net.CNetClient` 里
（`CSocket::Process/_Send/_RecvMost`）。要真正做到零 socket，必须替换 `net.g_Net`
这个全局对象——那需要改 `script.fls` 重打包 484 个脚本，风险与收益不成比例。
回环 TCP 的成本接近零（不走网卡、不出本机），换来客户端侧零改动。

**为什么不把 Python 宿主注入 `mx.exe`？**
目前检查到的客户端脚本没有可配置的宿主插件加载入口：`init.py` 重置 `sys.path`
并加载引擎提供的 `C_sys`，`game.py` 只有游戏辅助函数，`main.py` 的 `Start()` 是
客户端 UI 初始化流程；网络对象 `net.g_Net` 来自原生 `C_net`。同时客户端内嵌的是
CPython 2.6，而 `m4_server.py` 使用 Python 3 的文件编码参数、`exist_ok` 等接口，
不能直接导入该解释器。因而“把现有 Python 宿主塞进客户端进程”不是启动参数或
插件配置可以完成的改动。

要做真正的进程内服务端，需先选择并单独实现受控集成路径：将服务端改写为兼容
客户端 CPython 2.6 的模块并由可修改的脚本加载，或把服务端移植为客户端支持的
原生组件；还需处理客户端 `C_net` 与服务端传输之间的接口。当前项目没有证据表明
存在可直接使用的官方插件接口，因此本项目继续采用 loopback TCP；不把 DLL/进程
注入当作现成或已验证的集成方式。

**为什么 `port=0` 而不是固定端口？**
固定端口在单机场景只有坏处：占用即失败，且端口号散落在 `local.ini` /
`server7_local.bin` / `prepare_local_client.py` 三处，改一处漏两处。
`port=0` 让内核拿到真实端口后**反向生成**客户端配置，从结构上消灭不同步。

**为什么直启 `mx.exe`（提权），而不是免提权的 `gameplayer.exe`？**
`gameplayer.exe` 实为 .mwr **录像播放器**（窗口标题「录像播放器」、内嵌串
「是否退出播放器」、从不连模拟服）——2026-10-16 真机复核定案，**不是**游戏进程。
游戏入口是 `mx.exe`（内嵌 CPython 客户端，清单声明 `requireAdministrator`）：
`subprocess.Popen(mx.exe)` 在未提权会话下抛 `WinError 740`，因此宿主改走
`ShellExecuteEx(runas)` 提权启动（弹 UAC 确认框，与用户双击 mx.exe 的体验一致），
同时保留启动器内嵌浏览器的「脚本错误」模态框由本地 HTTP 劫持化解。

**为什么 HTTP 劫持必须进宿主？**
客户端 `update.ini` 把 `ServerList` / `MiniPage` / `DownPage` / `GuidePage`
全部指向 `127.0.0.1:8080`。不起这个服务会同时踩两个坑：
「服务器列表需要刷新」模态框，以及启动器内嵌浏览器的「脚本错误」模态框
（后者对 SendKeys / WM_CLOSE 均不响应，是启动流程唯一的人工干预点，
见 `local_http.py:45-51`）。因此 `server7_local.bin` 也要按真实端口重编，
否则刷新出来的列表会指向没人监听的 3134。

## 五、怎么跑

```bat
cd MX\服务端源码\sim
start_singleplayer.bat                 :: 一键单机启动
start_singleplayer.bat --fresh         :: 删档从零开始
start_singleplayer.bat --no-encounter  :: 纯探索，不遇怪
start_singleplayer.bat --web           :: 附带 GM 面板（仅 127.0.0.1:8080）
start_singleplayer.bat --save-dir D:\mxsj2013\单机存档
start_singleplayer.bat --no-client     :: 只起内核（脚本联调）
start_local_test.bat                   :: 兼容入口，等价于 start_singleplayer.bat
```

等价命令：`python m4_server.py --single`（同一宿主）。
也可直接双击 `start_singleplayer.bat`；旧的 `start_local_test.bat` 现已转发到同一入口，
不再分别启动 HTTP 服务、旧 mock 服务和客户端。
客户端仍按老流程操作：选服界面第一行「本地测试服」→ 帐号纯数字、密码 6 位。

**还原客户端配置**：`python prepare_local_client.py --revert`，或删掉客户端目录下的
`local.ini` 并去掉 `mx.ini` 的 `serverini=` 行。宿主每次改写前会留
`local.ini.bak_singleplayer` / `mx.ini.bak_singleplayer`。
